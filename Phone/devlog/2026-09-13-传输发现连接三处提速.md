# 2026-09-13 第八轮（手机端）：传输 / 发现 / 连接三处提速

用户要求："优化一下双端的文件传输速度、配对发现速度、连接设备速度。"
动手前先让两个只读 agent 把两端的热路径读了一遍（每处都带 file:line），按"证据 → 改动"来做，
不靠猜。

## 一、手机端：发现改走**广播优先**（9.3 秒 → 百毫秒级）

`ptpip/Discovery.kt` 原来分两段：已知地址（配对表 + 网关 + 本机）快扫；没命中再**逐个单播**
扫整个 /24 —— 254 个地址 × 4 个候选端口 = **1016 个 UDP 小包**，代码里自己记着实测
"要 9.3 秒"（发送本身阻塞；那些地址多半没有 ARP 表项）。

改动：在单播扫之前**先发广播**（子网广播 `x.x.x.255` + 受限广播 `255.255.255.255`，
每个候选端口各一个 = 8 个包）→ 几百毫秒收结果；广播被 AP 过滤时**才**退回原来的单播扫。

- 为什么可行：相机端探测口是 `bind(new InetSocketAddress(protoPort))` —— 绑的是**通配地址**，
  广播包它收得到（这一条是去读相机代码确认的，不是推测）。
- 兜底保留：广播在部分网络/AP 上会被丢，丢时就还是那条慢路，功能不回退。
- 装机实测：`扫描完成：…命中 1 台，thorough=true sweep=true，耗时 165 ms`（已知地址命中）。
  未命中地址时的广播路径要等相机换 IP 才能实测，单播兜底仍在。

## 二、手机端：数据连接的三处开销

1. **接收缓冲 1 MiB**（`DataChannel.download`）：这条连接是单向大流量，Android 默认的
   RCVBUF 直接封住 TCP 窗口上限。必须在 `connect()` **之前**设（窗口缩放是握手协商的）。
2. **进度回调合并上报**（`ObjectRepository.pumpToStream`）：原来**每 128 KiB** 一次，
   而上层每个回调要 `indexOfFirst` 找条目、替换一次 `SnapshotStateList`、再把整个队列扫一遍
   汇总 —— 25 MB 的文件就是 200 次 O(队列长度) 的活，全压在"边收边写"那条线程上，
   还顺带触发 Compose 重组。现在攒够 512 KiB 或隔 120 ms 才报一次，**最后一帧必报**。
3. **握手读超时**（`PtpIpClient`）：原来控制 socket 只有 connect 超时，握手那几次 `recvMsg()`
   是无限等的 —— 相机若"接了 TCP 但不应答"，手机就永远钉在"正在连接"上，而且整个 io 执行器
   被这次 `.get()` 占住，重连都排不进去。现在只在握手段临时设 SO_TIMEOUT，**用完清 0** ——
   控制连接建立后是"请求-应答"节奏（由调用方超时管），事件通道更是故意无限等。

## 三、⚠ 我自己引入的一个真 bug（已修，留档）

我还顺手做了一条"**复用收包缓冲**"（省掉每 128 KiB 一个新数组 = 每文件 25 MB 垃圾），
结果用户实测报回两个症状：**进度跑满又归零、循环往复最后失败** + **缩略图/预览图出现坏块**。

根因：`DataChannel` 判断"这一帧带了多少数据"用的是 **`dataLen(body) = body.size - 4`**，
而全工程（`parseOp` / `parseEvent` / `PtpIpClient` …）也都拿 `body.size` 当权威长度。
把 `body` 换成一块 128 KiB 的复用缓冲之后，`body.size` **恒等于缓冲大小**、不再等于本帧长度：

- 接收方按"每帧 128 KiB"累加 → 冲破对象总长 → 上层判短收/超收 → `FAILED` 并重试
  （表现就是"进度归零、循环往复、最后失败"）；
- 多写进去的**上一帧的旧字节**直接落盘 → 缩略图/预览图坏块。

**修法：撤掉复用**，`PtpCodec.read` 恢复原签名（那条 `reuse` 参数连注释一起删了，
免得日后有人再顺手加回来），并在 `DataChannel` 与 `PtpCodec.read` 各留一段长注释说明这个陷阱。
要用复用缓冲，就必须把**真实长度**从帧头一路带进 `Msg`、并把所有 `body.size` 判据换掉 ——
那是整个协议层的改动，为省这点垃圾不值得。

教训（值得单独记）：**复用缓冲的前提是"长度的权威来源不是数组大小"**。这个工程里
恰恰相反，所以"省一次分配"的收益是假的，换来的是静默的数据损坏。

## 四、相机端：数据帧零分配、单拷贝（等相机端新包装上才生效）

`PtpIpServer.transfer()` 原来每 128 KiB 走一次 `PtpCodec.dataPacket()`：
先 `new byte[4+len]`（载荷副本）、再由 `frame()` 拷进 `new byte[HEADER_LEN+n]`（整个帧）
—— **每块两次分配、每个字节拷两遍**，几十 MB 的文件就是几百 MB 的垃圾与 memcpy，
全落在相机那个很小的堆上，GC 抖动直接压住吞吐。

改成"就地"写法（`PtpCodec.DATA_PAYLOAD_OFFSET` / `dataFrameCapacity()` / `fillDataFrame()` +
`Conn.send(frame, off, len)`）：**一次传输只分配一块缓冲**，数据由 `readInto()` 直接读进
载荷区，包头 12 字节就地写 —— 一次拷贝都不做。

- 正确性：相机端桌面回归**全绿**，其中包含按**逐字节比对**的数据口取文件与分片续传断言
  （TestMain 21 / ProtocolTest 168 / PairingStore 57 / AppLog 12 / Batch 361）——
  这条改动等价于"已经过字节级验证"。
- 未生效：相机得装新包（相机没有 adb，要用户手动装，且**先卸载旧版**）。

## 五、顺带：悬浮窗设备行

- 「未连接（点此重连）」→ **「未连接」**，并且**点当前已选中那一行不再有任何响应**
  （`PanelRow` 的 `onClick` 收成可空，null 时渲染成不可点的 Surface，连水波纹都没有）。
  那一块只负责**切换设备**，重连交给主界面的按钮 —— 原来两者混在一行，想换相机时手一抖
  点到当前这台会把会话重启一遍。

## 六、验证与结论

- 装机实测：发现 165 ms（已知地址命中）；`receiveBufferSize`、进度合并、握手超时、广播 + 兜底
  都在新包里。
- **速度没看到明显变化**（用户实测）—— 但那次测量正好落在上面那个 bug 期间，数据不可信；
  修好后需要重量一次。
- 如果修好后速度仍然基本不变，那说明瓶颈在**相机的 Wi-Fi 链路本身**（相机 AP 的吞吐上限），
  而不是这两端的 CPU/GC —— 届时如实记录，不硬说"提速了"。这轮真正确定拿到的是：
  相机端**去掉了几百 MB 的分配与拷贝**（CPU/GC 余量）、发现路径在扫网段时**从 9.3 秒变几百毫秒**、
  以及握手不再可能无限挂起。
