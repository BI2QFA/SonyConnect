## 二、几何：先按 density=3.0 反推真值（两处独立印证）

**这一步我一开始就做错了。** 第一版是拿"元素占屏宽的比例"硬折算的，得到
圆钮 60dp / 药丸 274dp —— 全偏大。

正确做法是**先用两个已知的 Material 尺寸反推 density**：

| 参照物 | 实测 | 若为…… | 得 density |
|---|---|---|---|
| 圆形按钮 | 168px | 56dp（MD3 FAB 标准尺寸） | **3.00** |
| 通话记录行距 | 213px | 72dp（标准 ListItem） | **2.96** |

两条互相印证 ⟹ 参考图那块屏是 **400dp 宽**、density 3.0。于是各元素 dp 真值：

| 元素 | 参考 px | **dp 真值** | 我们（改前） |
|---|---|---|---|
| 圆钮直径 | 168 | **56** | 60 |
| 药丸 | 763×166 | **254×55** | 274×60 |
| 药丸↔圆钮间距 | 40 | **13.3** | 14 |
| 行左右边距 | 116 | **38.7** | 16 |
| 面板宽 | 1053 | **351** | 自适应 |
| 面板左右边距 | 74 | **24.7** | 12（仅右） |
| 面板圆角 | 90 | **30** | 28 |

★ 关键认识：**dp 本来就是与屏幕无关的绝对尺寸**，所以"完全一样"= 照搬 dp，
而不是照搬占屏宽的百分比。

### 屏幕装不下的取舍

参考图那块屏 400dp，我们只有 360dp：`38.7 + 254 + 13.3 + 56 + 38.7 ≈ 400` 放不下。
Compose 会把**固定尺寸的子项按比例压扁** —— 实测圆钮被挤成椭圆（截图里很明显）。

所以：**药丸与圆钮的尺寸一个不动**（用户点名要"完全一样"的就是这两个），
**边距改为按剩余空间自适应**（`coerceIn(8dp, 39dp)`）。360dp 屏上算出来两边各 19.5dp。

## 三、动画：三层叠加（逐帧量参考得来的）

### 参考的实测时序（90fps，整段 33 帧）

```
帧62-65  绿盘一边长大一边上移（168px→210→278，y 从 2390 升到 2180）→ 按钮"飞走"
帧64-65  原位采样从 (67,191,37) 掉到 (3,3,3)                        → 按**走了**
帧66-78  绿盘继续长到面板大小（678×134@y2198）                       → 变成面板
帧79-95  原位采样 46→61→116→152→189→207                            → 新图标**淡入**
```

### 落成三条曲线

| 动作 | 参考表现 | 实现 |
|---|---|---|
| ① 按钮飞上去 | 绿盘一边长一边上移 | 整块布局在终点位，绘制时按 `(1-p)` **平移**回按钮那一角 |
| ② 原位冒新图标 | 由虚到实、由小到大，且是**深色** | 头 10% 淡出旧钮 → 中段空档 → 55% 起新图标淡入+从 0.4 放大 |
| ③ 形状 | 正圆 → 圆角矩形 | `DiscShape` 自定义 `Outline`，分两段生长（宽高同步 → 单独撑宽） |

### 为什么分两段（而不是宽高同一个进度线性插值）

参考那个绿盘**全程是正圆**地长大 —— 因为它那块面板 1053×1038，**几乎正方形**。
我们的面板 640×496（1.29:1）：宽高同一进度插值的话宽度会长得快 1.29 倍，
几十毫秒后就变成**横椭圆**（第一版实测就是这个，"椭圆在摊开"，完全没有圆盘感）。

所以规则：**先让圆长到面板的高（宽高同步 = 真正的圆），高度到顶后再单独撑宽**。

## 四、★ 四处我写错的地方（这轮的主要收获）

### 错误 1：过冲被 `coerceIn` 裁掉了

```kotlin
// 错：弹簧照常过冲，但算出来的尺寸被夹在 1.0 → 画面上一动不动
val p = progress.coerceIn(0f, 1f)
```

用户看到的"没有过冲、不够 Q 弹"就是这个：**弹簧白装了**。

### 错误 2：把一条曲线硬拼成两段 → **顿挫**

修完错误 1 之后我改成"生长铺满 + 自己叠一条过冲脉冲"，结果用户报**顿挫**。
根因是**速度不连续**：生长段结尾仍是满速，脉冲起点速度是 0 ——
速度从最大**瞬间掉到零**。中间试过 easeOutCubic 收尾（速度连续了），
但两段的**加速度**在接缝处仍不连续，快速播放下还是生涩。

**最终解法：换掉"拼接"这个思路。** 直接用**欠阻尼二阶系统的单位阶跃响应**当 easing：

```
x(t) = 1 − e^(−ζωt)·[cos(ω_d t) + (ζω/ω_d)·sin(ω_d t)]
```

它本身就是一个真实弹簧的解析解，天然"从 0 冲过 1 再回落"，**处处无穷可导（C∞）**，
所以不可能顿挫；过冲量只由阻尼比一个参数决定：

| ζ | 过冲 |
|---|---|
| 0.80 | 1.5% |
| **0.667** | **6.0%** ← 采用 |
| 0.60 | 9.5% |

★ 取 6% 而不是参考反解出来的 1.3%：参考面板 1053px 弹 13px 看得见，
我们 624px 上 1.3% 只有 8px —— 手机上根本看不出来。

★ **必须归一化**：解析解在 t=1 处是 0.99869 而非 1.0，直接用会让 `progress`
**永久停在 0.9987**（静止态比终态小 0.8px）。除以它自己的终值即可。

### 错误 3：过冲画进形状里 → **灰底冲出框外**

我一开始把过冲做进 `DiscShape.createOutline`，让轮廓**长过布局盒**。
用户报"灰色背景在过冲时冲出框外"—— `clip()` 的轮廓超出图层边界之后，
绘制与裁剪的边界对不上。

**修法**：形状**永远只长到布局盒为止**（`discGeometry` 里把 p 夹进 0..1），
过冲交给 `graphicsLayer { scaleX/scaleY }` —— 缩放是绘制阶段的事，
天然可以超出边界。配 `transformOrigin = (1,1)` 就是"从右下角整块鼓一下"。

### 错误 4：硬截断把收起的过冲吃掉了

```kotlin
// 错：收起走 1→0，progress 从 1 递减，永远进不了"略大于 1"那个分支
if (progress <= 0f || progress >= 1f) return 0f
```

用户报"收起面板的小圆形的过冲动画仍然没有"就是这个 —— 两个方向都被吃掉。

**修法**：把"超出 [0,1] 的那部分"归一化成 **−1..+1** 的无量纲量，
**同一个来源同时驱动**面板缩放与按钮位移（相位天然一致，不会各弹各的）：

```kotlin
private fun overshootNorm(p: Float) =
    ((p - p.coerceIn(0f, 1f)) / OVERSHOOT_PEAK).coerceIn(-1f, 1f)
```

于是：展开鼓到 +6%（面板）/ +3dp（按钮），收起缩到 −6% / −3dp。

### 错误 5：收起时按钮**向上弹**（用户："为什么他会向上弹一下"）

`overshootNorm` 是**有号量**（展开 +1、收起 −1），而我直接把它交给了 `translationY`，
而 Compose 的 `translationY` **正值朝下**：

```
展开：norm = +1  →  translationY = +3dp  →  向下沉  ✔
收起：norm = −1  →  translationY = −3dp  →  向上弹  ✘
```

物理上说不通：那颗按钮是被**落下来的面板砸中**的，无论面板展开还是收起，
它都只该被**往下压**。所以符号必须固定朝下 —— `overshootNorm` 只给**幅度**，
方向由 `abs()` 定死，两个方向都走"沉一下再弹回原位"。

> 教训：一个量若同时携带"幅度"和"方向"两种语义，在传给不同用途时极易用错方向。
> 宁可让它只表达幅度，方向在消费点显式决定。

### 错误 6：按钮在**展开**时也过冲（用户："展开面板时只有面板需要过冲，下方的小按钮不需要"）

上一轮为治错误 5 用了 `abs()`，把**两个方向**都变成"向下沉" —— 但用户要的是
**只有收起方向才有**。

判据其实非常干净 —— **看 `progress` 超出的符号就知道方向**：

```
展开的过冲：progress 冲到 1 以上（>0）→ 按钮不动
收起的过冲：progress 掉到 0 以下（<0）→ 按钮下沉再弹回
```

所以只取负的那一半（`(-progress).coerceAtLeast(0f)`），正的直接返回 0，
不需要额外的方向参数。

### 调整 7：回弹速度与过冲幅度

- **按钮回弹放慢**（用户："收起的小按钮过冲回弹速度有点太快了"）：
  幅度曲线做 **`pow(0.65)`** 的时间重映射 —— 幂次 <1 会让曲线中段抬起来，
  峰值过后幅度**下降得更慢**，回弹拖得更长。线性映射时峰值到归零只占约 160ms，
  那一下显得急；抬起来之后一直是"缓缓归位"。
- **面板过冲幅度 6% → 4.5%**（用户："有点过大，稍微小一点点"）。

### 调整 8：新图标**不参与过冲**（用户："由小变大的过程中也不需要过冲"）

我上一版给 `newIconProgress` 特意写了"**不裁上界**"，想让它跟着 Q 弹一下 —— 那是错的：
`progress` 在展开时冲到 1.045，图标长到满尺寸后又缩回去一点，看起来像"冒出来之后抖了一下"。

改成**夹到 [0,1]**：`progress` 的过冲不许透进来。缩放再套一层 smoothstep
（`3x²−2x³`，两端导数都为 0）—— 起步轻、到位稳，就是用户要的"丝滑的出现"。

> 原则：**过冲只属于面板**（它是被用户"甩"出来的那块），
> 原位这个小图标是**跟在后面浮现**的，只需要干净利落地到位。

### ★★ 调整 10：**逐帧量原版**，把曲线与时长都改成实测值（本轮最重要的一次）

用户两次点出根本问题：**"不要偷懒，整个看一遍，看看原版的动画曲线是怎样的"**、
**"为什么你的动画如此僵硬而且很拖沓，这方面要完全向原版看齐"**。

前面几轮我一直在**凭手感调**（慢-快-慢 → 由快到慢 → 又改回慢-快-慢），每次都在
"猜另一条曲线"，从来没去量过原版。这次把 90fps 素材（540 帧 / 1200×2670）
**逐帧读完**，用面板宽度当标尺（圆钮 168px → 面板 1053px）反推 p(t)。

#### 量出来的三件事

**① 曲线形状：`easeOutQuad`（起步最快、一路减速）** —— 最小二乘拟合 8 条候选：

| 候选 | RMSE | |
|---|---|---|
| **easeOutQuad** | **0.042** | ← 原版就是这个 |
| easeOutSine | 0.069 | |
| easeOutCubic | 0.076 | 同档 |
| easeInOutCubic（慢-快-慢） | 0.247 | **差 6 倍** |
| easeInOutQuart（我上一版用的） | 0.263 | **差 6 倍** |

**② 过冲段是"缓慢爬升后停住"，不是"冲上去再弹回"** —— 这是**僵硬的根源**：

```
参考末段实测： +0.11% → +0.79% → +1.13% → +1.36% → +1.58%（然后一直保持 1.58%）
```

它是**一路慢爬**上去的；而我原来用的 `sin²(π·t³)` 鼓包是**急冲急回**
（峰值 t=0.85，到 t=1 又落回 1.0）—— 那一下"回弹"就是僵硬的来源。
现在改成：主体在 `KNEE=0.81` 处到位，之后 smoothstep **单调爬到峰值并停住**
（t=1 时正好等于峰值，不回弹）。

**③ 时长：展开 350ms / 收起 90ms** —— 这是**拖沓的根源**：

| | 参考实测 | 我之前 | 差 |
|---|---|---|---|
| 展开 | p0.50→89ms、p0.99→244ms、稳定于 267ms | 400ms | 偏慢 |
| **收起** | **56ms 走完全程**（1.0→0.89→0.82→0.65→0.58→0.50→0） | **250ms** | **慢近 3 倍** |

收起那个数字是我之前**读错了素材**：原版收起的主体只有 6 帧，我把 f183 之后
"面板位置冒出的 316px"当成了面板还在收 —— 那其实是**新图标在长大**。

展开 350ms 不是拍的：把参考的五个关键时刻分别反解"我的曲线需要多长"，
五点给出 335~375ms，取中位。这样两边**进度-时间关系**是对齐的，不只是总长相仿：

```
时刻      参考 p     我的 p     差
 89ms     0.500     0.529    +0.029
156ms     0.800     0.798    -0.002
189ms     0.900     0.889    -0.011
222ms     0.950     0.953    +0.003
244ms     0.990     0.981    -0.009
```

> 教训：**"手感像不像"这件事是可以量的**。我前面花了好几轮在猜曲线，
> 每次都被打回；一旦把原版逐帧读出来，一次就定死了。

### ★★ 调整 11：把曲线量**完整**（顿挫的真正来源）

用户："过冲动画有出问题顿挫了"。追下去发现是**曲线本身的三段拼接有问题**：

上一次我量的"过冲"只量到了**爬升段**，于是把曲线做成"爬到峰值就停住" ——
那在 `KNEE` 处速度要**从主体的一路递减突然变成 0**，接缝就是那一下顿挫。

**这次把整段量全了**，发现原版的过冲是**完整的两段**：

```
主体到 1.0（233ms）→ 爬到峰值 +1.58%（278ms）→ 回落（478ms 回到 1.000）
                                    ↑ 我一直漏掉的是这段回落
```

★ 漏掉的原因是个**测量坑**：`connectedComponents` 取最大连通域时，
"面板 + 下方新图标"会连成**联合外框**，末段宽度虚高 → 看不见回落。
必须**按面积筛出面板本体**（面积 >20 万才是），这个坑记在
`tools/fit_reference_curve.py` 的注释里。

最终曲线：

| 段 | 区间 | 形状 | 接缝 |
|---|---|---|---|
| 主体 | 0 .. 0.487 | `easeOutQuad` | 导数 0 |
| 过冲 | 0.487 .. 1.0 | Beta 鼓包 `u²(1−u)^8.8`（归一化），峰在 u=0.185、末尾归零 | 两端导数 0 |

Beta 函数两个指数都 >1 ⟹ **两端值与导数都为 0** ⟹ 与主体的接缝、以及末尾归位
都不会有速度突变 —— 顿挫消除。

### 调整 12：三处细节（用户一次提了三条）

1. **过冲以面板中央为放大中心** —— 我原来写的是 `TransformOrigin(1f, 1f)`（右下角），
   那是跟着**位移**的锚点走的。但位移与缩放是两件事：
   位移从右下角出发（那是圆钮的位置，对的），而"鼓一下"是**已经落位之后的呼吸**，
   从中心对称放大才自然；锚在角落会让整块往左下"长"，看着像又飞了一次。
   → 改成 `TransformOrigin(0.5f, 0.5f)`。
2. **速度过快** → 展开 480 → **550ms**。
3. **收起时按钮下落过冲没了** —— 这是我上一轮把收起压到 90ms 的副作用：
   按钮下沉的峰值在收起**末段**（`progress ≈ −0.045`），90ms 里那一段只采到
   1~2 帧、还被按钮淡入盖住。两处一起改：
   - 收起时长 90 → **180ms**（面板比参考的 56ms 缓，但换来按钮那一下可见 ——
     这两条**不能同时满足**，选了可见性，取舍写在 `COLLAPSE_MS` 的注释里）
   - 幅度曲线从线性改成 **`pow(0.6)`**（中段抬起来），峰值前后几帧都保持在 70%
     以上；幅度 3 → **4dp**
   → 收回来的逐帧：`3.23 → 3.70 → 2.00 → 0.64 dp`，4 帧可见窗口

### 调整 9（已被上面取代）：曲线在两种趋势之间来回摇摆

用户先说"所有的动画要有明显的**由快到慢**的趋势"，我照做换成
`easeOutCubic + 尾巴`（峰值速度 3.00）；随后改口"**算了还是改回原来的慢快慢吧，
但是慢快慢的变化要稍微明显一些**"。

所以最终形状定在 **慢-快-慢**，但比上一版更陡：

```
x(t) = easeInOutQuart(t) + A·sin²(π·t³)
       └── 主体：慢-快-慢 ──┘  └─ 过冲：只在末尾 ─┘
```

| 主体曲线 | 峰值速度 | 结论 |
|---|---|---|
| `easeInOutCubic` | 3.00 | 中段不够陡 |
| 阻尼弹簧（更早那版） | 3.54 | 平滑，但用户觉得"变化不明显" |
| **`easeInOutQuart`** | **4.00** | ← 采用（比弹簧再陡 13%） |
| `easeInOutQuint` | 5.00 | 太陡，那一下会"窜" |

- **主体 `easeInOutQuart`**：t<0.5 时 `8t⁴`、t≥0.5 时 `1−(−2t+2)⁴/2`。
  两端速度**和**加速度都是 0（真正的慢起慢收），中段冲到峰值 4.00。
- **过冲 `sin²(π·t³)`**：两端值与导数都为 0，只在末尾鼓一下（峰 t≈0.83）就落回，
  不干扰前面的慢-快-慢。用 `t³` 是把鼓包**往尾部推**（用 `sin²(πt)` 的话鼓包中心在
  t=0.5，中段就开始回缩，看着像"长过头再缩回来"）。
- **A 重新解过**：换主体曲线后，使 `max(主体+A·B) = 1.045` 的 A 从 0.05217 变成
  **0.05440** —— 换曲线必须重解这个数，否则实际过冲与标称值对不上。

导航栏里那些"用户看得出在动"的地方也一并切到同一条 S 形（`Motion.fastOut()` /
`fastOutFade()`，改名自 `FastOutEasing`）：指示块滑动、图标弹起、图标换色、箭头翻转。
`Motion.kt` 里的库弹簧**保留**给"数值追值"这类非视觉场合（进度环追百分比、
尺寸自适应）—— 它们不需要"看得出快慢"的观感。

★ 顺带把一个隐蔽的坑修了：过冲峰值原本分成**两个常量**写（`OVERSHOOT_PEAK = 0.061`
与 `PANEL_OVERSHOOT_PEAK = 0.045`），换算曲线之后就对不上了 —— 归一化分母与标称幅度
必须是**同一个数**，现在合并成一个 `OVERSHOOT_PEAK`。

### 附带：文字颤抖

`graphicsLayer` 缩放时，Android 会按**当前缩放比**逐帧栅格化文字，亚像素落点每帧
都不同 → 笔画边缘一直跳。修法是 `compositingStrategy = CompositingStrategy.Offscreen`：
内容按自然尺寸栅格化一次进离屏缓冲，之后缩放只当纹理采样。

## 九、最终一轮（第 12 轮）：按"串帧看"重做曲线 + 装机实测通过

> 用户原话："感觉面板的过冲不像是面板打开后因重力的自然回弹 而是刻意的弹了一下
> 面板收起的动画也没有轻飘飘的感觉 像是狠狠的砸了下来
> 按照我给你的原版视频做修改 你不要只读原版的动画曲线 你应该把每一帧动画都联系起来"

**这一轮的关键是换了一种看法**：不再"读曲线"，而是**把原版的相邻帧一帧帧摆开看**，
才看出两件事之前全看错了。

### 9.1 展开的过冲不是"对称鼓包"，是"停住→缓慢飘回"

之前所有版本都把过冲做成 `sin²` / Beta / 解析弹簧——**全是对称脉冲**：
上去→到峰→原路下来。看着就是"刻意弹了一下"。

串帧之后才看清原版是：

```
生长到峰 → **停住 44ms**（采样点不动） → **以恒定微速**漂回 1.0
```

这是**过阻尼**（ζ>1）的回落，不是欠阻尼的振荡。
对应实现把 `overshootEasing` 从"对称鼓包"改成分段：
`easeOutQuad 主体 → smoothstep 爬峰 → 44ms 平台 → 线性恒速漂回`。

### 9.2 收起是**两段独立动作**，不是"展开的反放"

之前的收起把 `progress` 从 1 拉回到 0，等于把展开曲线反着放了一遍——
"先慢后快再慢"地一路缩到底，就是用户说的"狠狠砸下来"。

串帧看原版收起其实分两步：

```
第 1 段（0..55ms）  面板自身**越缩越快**地坠落、消失   （easeInCubic）
第 2 段（100ms 起） 原位的深色新图标**由大到小**缓缓上浮落位（316→168px）
```

面板只承担前 55ms，之后画面里全是图标浮现——整个后半程是"轻"的。
对应实现把 `collapseEasing` 改成 `t³`，并加 `PANEL_EXIT_AT = 0.70`
（面板提前退出，图标从那一刻开始浮现）。

### 10.1 逐帧实测（这次连"两颗按钮"一起量）

量法：面板本体取灰阶连通域；两颗按钮分别取绿色阈值与"非纯黑"阈值，
在按钮槽位（x 860..1160, y 2385..2615）内取包围盒。

```
【展开】绿色(紫) → 面板          黑色钮从无到有
  f62-64   绿钮 166→210→278     一边长大一边上移 → 已经是面板了
  f70-86   面板 0.53→0.99 σ     深钮 128→168px  由小到大、由虚到实
  f92      面板落位 1067px      深钮 168px      ★ 同时到位

【收起】深钮先走 → 空档 → 绿钮飞回
  f174-176  面板 1053→621→无     深钮 161→148→无  ★ 同时退场（55ms）
  f179-186  （空档 89ms）         画面里只剩导航栏
  f187-202  绿钮 0→182→168px     由虚到实、**略大着落位再收回**（1.083×）
```

★ 收起段最容易被忽略的一点：**绿钮出现时是 182px（终值 168px 的 1.083 倍）**，
再收进去 —— 也就是**回位带过冲**，而深色钮那颗**全程不过冲**。
两者不能用同一条曲线。

### 10.2 被推翻的三处旧结论

| 旧结论 | 实测真相 |
|---|---|
| 过冲是"爬到峰值就停住" | 峰值后有**约 200ms 的缓慢线性回落**（1067→1053px） |
| 收起是"面板一路缩到底" | 面板只承担前 55ms，之后是 89ms 空档 + 绿钮飞回 178ms |
| 按钮只有"一个 presence 透明度" | **两颗独立的按钮**，各自有 alpha/scale，且**必须互斥** |

### 10.3 ★★ "紫色按钮消失了，只有一种按钮状态"——病根

两颗按钮的进度函数**各自独立、没有互斥**：
收起静止时 `buttonPresence = 1` **且** `newIconProgress = 1` ——
两颗都画在最上层，深色那颗盖住紫的，于是任何时刻看到的都是同一个样子。

修法不是"再补一个条件判断"，而是把**两颗按钮当成一个状态机**：
用一个 `buttonState(expanded, progress)` 同时算出两颗的 alpha/scale，
让它们的互斥关系**体现在代码结构里**（一个函数返回两条完整状态），
而不是靠散落各处的 `if` 维持。

### 10.4 ★★ "收回动画闪烁" —— `Easing` 的方向反了

这条最隐蔽，也最该记住。`tween` 的 `easing` 是**归一化映射**，
必须满足 `easing(0)=0`、`easing(1)=1`，`animateFloatAsState` 按
`value = 起点 + (终点−起点) × easing(t)` 求值。

重写形状时把它写成了 `(1−t)²`（1→0），于是收起时
`value = 1 − (1−t)²` —— **progress 从 0 爬到 1，方向整个反了**：
开头一步跳到 0（面板被抹掉）、再一路涨回 1（面板又长回来），
画面就是来回抽动。录屏逐帧量到的现象是"面板静止 100 帧后一帧消失"。

正解：要 `progress = (1−t)²`，easing 就该写 **`1 − (1−t)²`**（仍是 0→1）。
★ 教训：**自定义 Easing 必须验端点**，`f(0)`、`f(1)` 各跑一次是几秒钟的事。

### 10.5 "窗口消失太快" → 交叉淡出（crossfade）

上一版让面板在 51ms 内淡掉（照抄原版的 55ms），但我们的面板是 624×496，
51ms 内边界还在大尺寸上就没了，读起来是"唰地消失"。

改成**与紫钮对称交叉**：
```
0..133ms    面板全不透明地一路缩小              "窗口缩小"
133..215ms  面板淡出 ‖ 紫钮淡入（进度范围等长）  "渐变为图标"
215..300ms  只剩紫钮，长大到 1.083 落位          "落位"
```
★ 关键是**紫钮的起点缩放取 1.84**（= 面板开始淡出时的盘径 309px ÷ 按钮 168px），
这样交接瞬间两个圆**大小、位置都重合**，读起来是"同一个圆在换颜色"。
取 1.0 或 0.4 都会让交接处出现"大圈 + 小圆"并存，反而像凭空消失。
