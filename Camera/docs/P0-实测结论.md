## 二、端口可用性 —— 18 个候选**全部空闲**

```
15740 15741 15742 15743 15744 15745 15746 15747 15748 15749
25740 25741 25742 35740 45740 55740
2121  2122
```

**结论：**

- ★ **15740（标准 PTP/IP）未被固件占用。** 相机正常 GUI 空闲态下，固件那个
  `libInfraPtpControl.so` / `PtptIp`（initSocket/Accept*/bind/listen）**并没有在监听 15740**。
  → 控制端口**以 15740 为首选是可行的**，原先"高风险"的担忧在本态下不成立。
- `2121 / 2122` 空闲属**预期**：测试时 SonyConnect 未运行，其 FTP / 私有协议服务未启动。
- ★ **保留意见（不推翻结论，只作为保险）**：本次是在**相机空闲态**所测。固件 `PtptIp` 若只在
  特定模式（如 PC 遥控 / 传输模式）激活，理论上仍存在"运行时被抢口"的可能。
  → **候选回退列表照留**（成本极低），并把实得端口经发现流程通告给手机端。

## 三、加密能力 —— 充足（超预期）

| 项 | 结果 |
|---|---|
| AES/CBC + HMAC-SHA256 | **有** |
| AES/GCM | **有** |
| 屏幕结论行 | `CBC+HMAC(有) / GCM(有) → 走 Encrypt-then-MAC` |

★ **重要更正**：方案 6.2 原写「`AES/GCM` 在 API 16 很可能**不可用**（GCM 一般要 API 19+）」——
**实测证明 GCM 可用**（该固件自带 provider，非标准 Conscrypt）。

**但仍然选 Encrypt-then-MAC（`AES-128-CBC` + `HMAC-SHA256`），理由：**

1. 文件走**分块流式加密**，CBC+HMAC 的 IV / 帧序号管理更简单、更可控；
2. 避免 **GCM nonce 重用**这个"一次失误即密钥报废"的致命坑（老设备 RNG 容错低）；
3. CBC+HMAC 是方案安全层已定稿的形态，API 16 上是原生稳的路径；
4. GCM 记入配对记录的 `cryptoSuite` **备选位**，将来若要可切换，不写死。

## 四、方案微调清单（据实测）

| # | 原方案 | 微调 |
|---|---|---|
| 1 | 15740 有被固件抢占的**高**风险 | 降为**低**；15740 作首选；候选回退 `[15740,15741,25740]` 保留作保险 |
| 2 | 6.2「GCM 很可能不可用」 | **更正为 GCM 可用**；默认仍 EtM；`cryptoSuite` 保留 GCM 选项位 |
| 3 | ECDH / DH 2048 退路（6.2） | **不需要**：方案明确"不做前向保密"，配对 prekey 用随机值即可，密钥交换不依赖 ECDH/DH |
| 4 | P0-3 AES 吞吐基准（决定决策 3 默认值） | **按要求移除、未实测**；决策 3 按"**默认开 + 可协商明文**"执行，真机联调若掉幅大再走明文 |

## 五、未回传项（非阻塞）

屏幕上另有 `AES-128 / AES-256 密钥生成`、`ECB / CTR / CFB`、`PBKDF2(SHA1/SHA256)`、
`SHA-256`、`SecureRandom 熵`、`ECDH 密钥协商` 各行结果；本次只转述了 CBC+HMAC 与 GCM 两行。

这些**不改变任何决策**：加密方案已定为 EtM（CBC+HMAC），密钥交换不依赖 ECDH/DH。
