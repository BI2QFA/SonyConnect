# 传输进行中文件页读不出目录 —— 根因与修复

**症状**（用户实测）：正在传文件时点开文件页，目录**刷不出来**（一直转圈）。

**结论**：手机端 `ObjectRepository` 只有**一条** IO 线程，整对象搬运（`pumpToStream`）
在这条线程上一跑就是几十秒，控制面的 `list()` 排在它后面 —— 而 `list()` 的
`submit{}.get()` **没有超时**，所以它既不会失败也不会返回，界面只能一直转圈。
不是相机的问题，也不是"传输中禁止浏览"的设计。

---

## 一、机制

```
DownloadService.drainQueue()            FilesScreen.load()
   └─ ObjectRepository.pumpToStream()      └─ ObjectRepository.list()
        └─ ioExecutor.submit{...}.get()          └─ ioExecutor.submit{...}.get()
           ↑ 同一个单线程执行器，一个 25MB 对象要占住它几十秒
```

日志佐证：用户复现窗口里 `ObjectRepository: list failed` **一条都没有** ——
不是报错，是**没返回**（`list()` 的 `.get()` 无超时，`loading` 状态永不落地）。

那为什么当初要串行？类文档写的是"控制面与数据面并发会让大文件传输被打断"，
怕的是相机端的单客户端语义。但相机端的实际机制是：

- 每条连接一个线程（`acceptLoop` → `newThread("ptpip-conn-" + c.id, c)`），
  控制连接与文件连接**本来就各跑各的线程**；
- 会踢连接的是"同 deviceId 的**第二条控制连接**"（`evictOrReject`），
  而手机端控制面只有一条控制连接，数据面走的是**文件端口**，两者不冲突；
- 相机端共享状态只有令牌表（`synchronized (pending)`）与缩略图记忆化
  （`synchronized (memoLock)`），都已是线程安全的。

也就是说"串行"从来不是正确性要求，只是没人把两件事拆开。

## 二、修复（手机端单侧，相机端一行未动）

`ObjectRepository` 拆成两条单线程执行器：

| 执行器 | 线程名 | 职责 |
|---|---|---|
| `ioExecutor`（控制面） | `PtpIpIo` | `list` / `stat` / `ping` / `deviceInfo` / `thumbQueue` / `exitApp` / `pairRemove` / `connect` / `pair` |
| `xferExecutor`（数据面） | `PtpIpXfer` | `pumpToStream`（原图下载）、`fetchObject`（缩略图 / 大预览） |

两条都仍是**单线程**，只是不再互相排队：

- 控制面单线程 —— 相机端单客户端语义、同一条控制连接上的串行往返不变；
- 数据面单线程 —— 相机端一次只撑得住一条数据连接、带宽该给传输独占不变。

因此传输期间：目录照读、心跳照跳（心跳顺带不再被传输拖住，电量/镜头在传输中也能刷新）。

## 三、验证

### 3.1 相机端前提 —— 桌面实测（新增 ④ 段，9 项断言）

`desktop-test/ProtocolTest.java` 新增 `concurrencyChecks()`：桩里加了 8 MB 的
"慢对象"（每次 128 KiB 分块读人工延时 40 ms → 约 2.5 秒的真流式传输窗口），
后台线程用**真文件端口 + 真 socket** 搬它，同时在同一控制连接上发控制请求：

```
=== ④ 传输进行中的控制面应答（文件页能否读目录）===
[PASS] 并发段：控制连接建立
[PASS] 慢对象 GET_OBJECT 受理（RC_OK）
[PASS] 并发段：传输窗口有效（对象仍在传输中）
[PASS] 传输期间 LIST_DIR 仍受理（文件页能读到目录）
[PASS] 传输期间 LIST_DIR 未被对象传输挡住（实测 0ms < 1000ms）
[PASS] 传输期间心跳仍受理（不会误判失联）
[PASS] 传输期间 STAT 仍受理（续传前校验可用）
[PASS] 中途插入的控制请求没有打断对象传输
[PASS] 并发传输回来的字节与源逐字节一致
```

这组断言把"相机端能在传输时照常应答"从假设变成**每次回归都会被量一遍**的事实
（手机端怎么分线程都没用，若相机端做不到，目录请求会在 8s 请求超时上撞死）。

### 3.2 手机端

`:app:assembleDebug` 通过；构建产物 `dex` 字节级检索到两个线程名
（`PtpIpIo` 与新的 `PtpIpXfer`），确认分线程确实进了包。

## 四、行为边界（不是 bug，是既有设计）

- **缩略图在传输期间仍是"暂停"状态**：`ThumbStore.pauseForTransfer()` 让拉取线程挂起，
  相机端预取队列也发了 `OP_THUMB_QUEUE_PAUSE`。所以传输中打开文件页会看到
  **文件名/大小/时间正常、缩略图位显示占位或转圈**，传输一结束（`resumeAfterTransfer`）
  自动补齐。这是为了不抢传输带宽而刻意保留的 —— 用户刚认可的那份传输速度就靠它。
- **点开单张全屏预览（大预览 ≈425 KB）** 与传输排在同一条数据面线程上：传输中打开会
  等当前这个文件传完（不是等整批）再显示，期间是"转圈"。把大预览也挤进传输的带宽
  不划算，所以保持排队。

## 五、待真机复验

1. 选中一批文件开始传输 → 切到文件页：**目录应立即列出**（名称/大小/时间），不再转圈到底。
2. 传输期间在文件页里进目录、翻页：应正常响应。
3. 传输期间顶栏电量/镜头信息应继续刷新（心跳不再被传输拖住）。
4. 传输结束后缩略图自动补齐（预期会陆续出现，非一次性）。
