# 2026-09-12 性能返工：传输太慢 / 发现太慢 / 配对太慢

首次真机联调结论：**功能全部正常**（配对、浏览、预览、下载、断点续传、遥控退出都通），
但三处慢：**传文件慢**、**发现设备慢**、**配对慢**。这一轮只解决这三件事，不动功能语义。

> 说明：本轮所有改动都**还没有真机复测**。下面的耗时数字都是代码里逐条推出来的量级
> 估算（标注为"估"），真机数字要靠新增的日志读回来 —— 见最后一节。

## 一、传输慢：每块都在重新打开 SD 上的文件

**病灶**（相机端 `PtpIpServer.transfer` → `PtpCameraHandler.readObject`）：

```java
// 每个 64 KiB 块都走一遍：
new RandomAccessFile(f, "r"); raf.seek(offset); raf.readFully(out); raf.close();
// 外加 readObject 开头那一次 f.isFile() —— 又一条 stat
```

逐块 open/close/stat 在相机 SD 是**毫秒级**的固定开销，而 64 KiB 一块意味着
**每 MB 要付 16 次**。24 MB 的 ARW ≈ 384 块 ≈ 光固定开销就几秒（估），
比顺序读本身还贵 —— 传输慢的主因就在这里。

**改法**：

1. `PtpIpServer.Handler` 新增可选能力 `openObject(path, kind) → ObjectReader`，
   一次传输只开一次句柄、逐块 `readInto` 读进目标缓冲。返回 null 时服务端自动
   回退到原来的逐块 `readObject`（功能不变，只是慢）。`transfer` 用
   try/finally 保证任何路径（正常/异常/取消/停机）都关句柄 —— SD 句柄不能攒着不放。
2. `readInto` 直接把数据读进**帧缓冲**，连"读出来再拷进载荷"那一次都省了。
3. 分块 64 KiB → **128 KiB**（`CryptoSuite.CHUNK`）：每块的固定成本减半，
   峰值内存仍只有 ~260 KB 量级。
4. 加密与封包的去重（`CryptoSuite.Stream`）：
   - `Cipher.getInstance` / `Mac.getInstance` 原来是**每帧**都付（前者要走一遍
     provider 查找并新建 native 密码上下文）。改成每连接一个 `Stream` 复用实例。
   - `sealInto` 把密文直接写进最终帧缓冲，`sendDataFrame` 直接把明文载荷封包 ——
     原来一块 64 KiB 要在 `PtpCodec.dataPacket` / `sendFramed` / `sealFrame` /
     `Session.seal` 之间来回拷 **3 次整块**，现在只剩 1 次。
   - `Session.seal/open` 现在就是"新建一个一次性 Stream"的薄封装 —— **线格式由
     唯一一份实现决定**，不再有两份可能分叉的加解密代码。
5. **加了可测量的日志**：每次传输结束记
   `传输完成 <路径>，共 N 字节，耗时 X ms（Y.YY MB/s）`。
   下次真机一看日志就知道现在到底多少 MB/s，以及还该不该继续抠。

`Stream` 是**非线程安全**的（`Cipher`/`Mac` 有状态），所以是"每条连接一个"：
相机端每条连接一条线程，正好一对一。

## 二、发现慢：候选端口被顺序轮询，一次扫描至少等满 4 个窗口

**病灶**（手机端 `Discovery.scan`）：外层 `for (port in CANDIDATE_PORTS)`，
每轮 `collect` 都等满 `ROUND_TIMEOUT_MS = 420ms`，**而且每轮重新给整个 /24 发一遍**。
相机只绑其中一个端口，所以哪怕第一轮就打中了，循环照样跑完后 3 轮 ——
**最快也要 1.68 s**，全部落空也是 1.68 s，外加每轮 254 个包白发包。

**改法**：

1. **已知地址快扫**：配对表里的相机 IP + 网关 + 本机 IP 先打一枪，窗口 260 ms。
   热点/Direct 模式下相机地址基本固定，绝大多数情况这一步就打中（估 ~150-200 ms 出结果）。
2. **候选端口一次全打**：4 个端口同轮发出、一个窗口收完。相机只绑一个端口，
   多收 3 个几十字节的 UDP 小包，换掉 3 个完整等待窗口 —— 这笔账很划算。
3. **静默早退**：收到过应答后，连续 150 ms 没有新应答就收工（接收粒度降到 50 ms）。
   局域网的应答是毫秒级的，等满 420 ms 纯属浪费。
4. 全子网补扫仍保留（相机换 IP 时靠它找回来），但只在快扫一无所获时才做。

**一处刻意保留的例外**：`thorough` 参数。自动扫描要"最快的那个设备"，命中即停；
但用户手动点"扫描设备"时**不早退**，老老实实扫完整个子网 —— 否则第二台相机
（比如新买的那台、还没配对的）永远看不见。

## 三、配对慢：PBKDF2 落在关键路径正中间

**病灶**（相机端 `pairingExchange`）：`K_pair = PBKDF2(6 位码, saltC, 20000, 32)`
是在收到 `PAIR_BEGIN` **之后**才现算的。老固件上纯 Java 的 20000 轮 HMAC 是**秒级**的，
而手机正卡在 ② 处等这个回包 —— 配对握手里最长的一段等待就是它。

**改法**：把盐从"每次尝试随机"改成"**每个窗口随机**"，于是整个窗口期内
`(码, 盐)` 都不变 —— 相机可以在**开窗那一刻**就把 K_pair 算好（后台线程），
用户低头敲 6 位码的那几秒正好把它盖掉，配对 ② 直接命中，零等待。

- 安全性没有削弱：盐仍然每个窗口都换，码本身也是每窗新生成的随机 6 位数字。
  盐的职责（防止跨窗口预计算复用）不受影响。
- 代次校验：用户在派生途中退出配对页又重新进入（换了码与盐）时，旧线程算完的
  那份会被丢弃，不会发布成当前窗口的密钥。
- 服务端保留回退：`pairingKey(salt)` 返回 null 就现场算，功能不受影响。
- `PairingStore.KDF_ITERATIONS` 与 `PtpIpServer.PAIR_KDF_ITERATIONS` 必须相等，
  有断言守着（`PairingStoreTest`）—— 数值分叉会让配对在 ② 处莫名其妙失败。
- 日志会记 `配对码预派生就绪，耗时 X ms`，真机顺带把相机的 PBKDF2 成本测出来了。

## 四、手机端收包：少拷两遍

`DataChannel` 原来每块要把密文拷一份（`copyOfRange`）、解出明文后再拷一份
（`payloadOf`），写盘还要再经一次 `out.write(chunk)`。现在：

- `SessionCrypto.Stream.open(seq, aad, buf, off, len)` **直接在帧缓冲的区间上**
  验 MAC + 解密（密文不再单独拷一份）；
- `onChunk` 回调改成 `(buf, off, len)`，落盘走 `out.write(buf, off, len)`，
  明文也不再拷一份。
- `PtpCodec.read` 不再先 `input.read()` 单字节探 EOF（数据通道是 128 KiB 的大帧，
  每帧一次单字节系统调用在这个量级上就是白付），改成一次性读满包头。

⚠️ 这里刻意**没有**加 `BufferedInputStream`：128 KiB 的帧体在缓冲层里反而会被
多拷一遍，而无缓冲的 `readFully` 循环本来就只有几次系统调用。

## 五、顺手补的一道门：桌面回归原来在用错误的编译器

改 `transfer` 时踩到一个真坑：`private static String throughputText(...)` 写在
内部类 `Conn` 里。相机端 `sourceCompatibility = JavaVersion.VERSION_1_6`，
**Java 1.6 不允许内部类里有静态方法** —— 装包时 Gradle 报错，但**桌面回归全绿**。

原因：`run-tests.sh` 用的是 `JAVA_HOME="${JAVA_HOME:-...jdk1.8...}"`，环境里已经
设了 JAVA_HOME（JDK 21）时就用 JDK 21 编译，源码级默认 21 自然放行。也就是说
这道"桌面门"一直在用一个和相机完全不同的编译器，**它其实挡不住工具链类的问题**。

**改法**（`desktop-test/run-tests.sh`）：

- 编译器**固定**用 a6300-tools 的 JDK 8（要用别的得显式给 `A6300_JDK`），
  并在第一步打印 `javac -version`，让用的哪个编译器一眼可见；
- 内核源码用 `-source 1.6 -target 1.6` 编译（与 build.gradle 一致），
  测试入口用默认源码级（它们不在相机上跑），分两次 javac。

代价：第一次跑就会暴露所有 1.6 违规。收益：这类"桌面绿、装包炸"的假绿不会再出现。
