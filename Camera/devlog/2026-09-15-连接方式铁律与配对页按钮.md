# 2026-09-15 相机端：MENU/弹窗三条铁律 + 配对页按钮 + 热点信息块

用户这一轮把三条**铁律**先立下来（大意）：

> 记住几条铁律
> 当没有选择连接方式时 一律弹窗提示选择连接方式
> 当没有已配对设备时 一律弹窗提示配对
> MENU键的功能为返回上一层级 也就是上一次显示的界面 当处于第一层级也就是没有可返回的
> 界面时 menu键功能为退出软件 此规则应应用于所有界面

然后是三件事：

> 把主界面热点模式下的"显示二维码"改为 热点信息 点击后应该是左边显示相机热点ssid和密码
> 右边显示二维码
> 配对界面下也应该显示类似于主页面的按钮 热点模式显示"热点信息""服务状态"
> wifi模式显示"Wi-Fi设置""服务状态"
> 服务状态界面的状态那行 如果处于配对模式应在后面加上括号 括号内内容配对模式

三条铁律落成什么（这一节是这一轮的核心）：

| 铁律 | 落点 |
|---|---|
| 没有连接方式 → 弹选择界面 | `onResume`（`savedMode == null` 直接给面板）+ **新增的两颗按钮**那条"键一=连接方式"的路（`onBlockButton` 的 else 分支） |
| 没有已配对设备 → 弹配对提示 | `requestPairing()`（原有）+ `goBackOneLevel()` 里新收的守卫 |
| MENU = 返回上一层，第一层 = 退出 | **`navHistory` 历史栈**（本轮重写，见下） |

## 一、MENU：从"一屏一个字段"改成**一份层级历史**

换装那版是"上一级"**一屏一个字段**写死的：`pairingBack`（配对页）、`confirmBack`
（弹窗）、`aboutFromPairing`（关于页）、加上 `onMenuKey` 里主界面/菜单/设备页/连接设置
四段手写分支。十来个屏就有十来处判据，每加一屏都要替它想一遍"它从哪来" ——
而"上一次显示的那个界面"本来就是**导航历史**的属性，不该由每一屏自己维护。

现在只有一份历史：

```java
private final java.util.List<Integer> navHistory = new java.util.ArrayList<Integer>();
private int baseScreen = -1;          // 最近一次显示的**基础屏**（浮层的上一级就是它）
```

由 `showScreen(target, back)` **唯一一处记帐**（`recordHistory`），规则四条：

1. **浮层不入栈** —— 确认框/通知框/切换浮层不是"一个去处"，它的上一级就是它压着的那一屏；
   从浮层往基础屏跳时，入栈的是 `baseScreen`（浮层只是过路）；
2. **落到主界面 = 回到第一层** → 历史全清。主界面永远是根（`MENU` 在这儿就是退出软件，
   不能因为"刚才从菜单绕进来"就变成回菜单）；
3. **关掉浮层（落点 = 它压着的那一屏）不入栈** —— 那是取消/关闭，不是往前走；
4. **同一屏不重复入栈** —— 否则"从配对页绕一圈回配对页"会在栈里压两个配对页，
   `MENU` 第一下变成"回到自己"：配对窗被重开、码也换了。

`onMenuKey()` 于是只剩两条路：**浮层**上只做"关掉它"（回到 `baseScreen`，
**不执行浮层上的动作** —— 那是确定键的事；通知借的面板顺手归位），
**其余屏**一律 `goBackOneLevel()`：弹栈顶，栈空 = 第一层 = 弹退出确认。

★ 顺带删掉三个字段与一个方法（`pairingBack` / `confirmBack` / `aboutFromPairing` /
`notePairingBack`）——它们的活全归 `navHistory`。`promptPairingRequired()` 里那段
"浮层上弹浮层要把上一级硬掰到连接设置面板"的**特判也一并消失**：
`baseScreen` 天然就是"最近一次显示的基础屏"，首启与"正在切换模式···"底下压着的
都是连接设置面板，同一件事由同一份状态给出。

★ 与两条弹窗铁律的接口收在 `goBackOneLevel()` 一处：**弹出来的落点**如果是主界面或配对页、
而本机一台已配对设备都没有，就不落过去，改弹"请先与一台手机配对"
（按确定进配对页）。老代码在 `SCR_MENU` 分支与 `SCR_ABOUT` 分支各写了一遍同样的判断，
现在只有一份。

★ **接入点模式/连接设置面板的底栏提示不再是假话**：面板的 `MENU` 后面那块，
有上一级时是返回箭头、第一层（首启直接弹出来的）时是**"退出"**两个字 ——
由 `showScreen(SCR_MODE)` 按 `navHistory.isEmpty()` 切换两个控件（图标字体的私有区
没有汉字，所以是"箭头控件 + 退出控件"两个，切可见性）。

## 二、`screen = -1`：第一屏到底算第几层

`screen` 的初值原来是 `SCR_MAIN`。但 XML 里 `screen_main` 虽然默认可见，
**它算不算"第一层"取决于启动路径**：有连接方式时它就是第一层（MENU=退出），
首启时第一屏是连接设置面板（主界面根本没露过脸）。初值给 `SCR_MAIN` 会让首启的
连接设置被记成"从主界面来的"，`MENU` 回主界面而不是退出。

所以 `screen = -1`（= "还没显示过任何一屏"），`onResume` 里走"有连接方式"那条路时
再补上 `screen = baseScreen = SCR_MAIN`（那一屏确实是主界面）。`showScreen` 里加了
一条兜底：收到非法屏号就落主界面 —— 一屏都不显示会是**黑屏且出不去**。

## 三、主界面：热点模式左键 → **热点信息**（左名称/密码，右二维码）

《把"显示二维码"改掉》的物理理由很实在：原厂那块二维码只有一个码，用户得先知道
热点叫什么、密码多少。改完这一块是"左两行字 + 右一个码"：

- 左：`热点名称：DIRECT-xy:ILCE-6300` / `热点密码：1234567890`，32px 单行（`PfT32`），
  框宽 400，行 y=76 / 136 —— 与右边那块二维码（160×213 @y24）竖向对齐成一块；
- 右：`qr_view` 从"居中"挪到 **x=452**，说明行跟着走；两者都止步于按钮行（270）。

**宽度是量过的**，不是估的（`tools/ui` 里有原厂字体）：
`热点名称：DIRECT-xy:ILCE-6300` 在 32px/0.7001 下需 **331.8px < 400**（余量 17%）；
同一把尺子量 `本机设备码：3f9a1c07be442d10` 在 38px 下得 **386.5px**，
与 devlog 里早就记下的 386px 一致 —— 尺子对得上。

## 四、配对页：与主界面**同构**（三块正文 + 常驻两按钮）

用户要"配对界面下也应该显示类似于主页面的按钮"，于是配对页正文改成与主界面一模一样的
结构：**三块互斥内容 + 一排常驻按钮**，只是第 0 块从"连接示意"换成"配对码"。

| 块 | 主界面 | 配对页 |
|---|---|---|
| 0 | 连接示意（相机 ↔ 手机） | 6 位码 + 倒计时 + 提示 |
| 1 | 热点信息（左名称/密码，右二维码） | **同一份内容** |
| 2 | 服务状态 | **同一份正文** |
| 左键 | 热点信息 / Wi-Fi 设置 / 连接方式 | **同一份文案、同一个方法** |
| 右键 | 服务状态 | 服务状态 |

- 第 0 块整块在按钮行（270）以上居中（原来是在整个正文区里居中，加了按钮行之后
  那样会顶到按钮上）；
- 两屏的正文/按钮在代码里**由同一组方法填**（`refreshScreens` / `updateStatusTexts` /
  `updateHotspotTexts` / `updateQrCode`），内容永远不会各写一套；只有 XML 里的控件是两份
  —— 同一个 Activity 里同 id 的控件不能有两份（`findViewById` 只认第一个），
  这一点在字段区那段注释里写明了；
- 1s 心跳从"只在主界面跑"扩到"主界面 + 配对页"：服务是后台起来的，等它就绪时用户
  多半已经在配对页上，"服务状态"那一块不能停在进屏那一刻的旧文本。

## 五、服务状态：状态行加"（配对模式）"

判据是**配对窗口开着**（`pairingStore.isOpen(now)`），不是"当前画的是配对页"：
窗口才是"正在等手机输码"这一事实（离开配对页就关窗）。所以启动中/运行中/失败/关闭
四态都可能带上它 —— 配对页最常见的时刻恰恰是服务还没起来的"启动中…"。

实测宽度：`状态：启动中…（配对模式）` 在 38px/0.7001 下 345.8px < 612（正文宽），
不会折行、不会把第 6 行挤到按钮底下。

## 七、这一轮**特意不动**的两处（先说清，免得当成漏做）

1. **"配对页上弹浮层会把配对窗关掉"**：`showScreen` 里那句
   `prev == SCR_PAIRING && target != SCR_PAIRING → leavePairingMode()` 用的是**屏号**，
   浮层目标（`DLG_CONFIRM`）也算"不是配对页"，于是窗口被关 —— 而回来时
   `enterPairingMode()` 会开新窗、**换一张新码**。这正是原来实现"配对码连错 5 次
   → 提示 + 自动换新码"的机制（那条提示的字面就是"已自动更换新的配对码"），
   是真机验过的行为。要"弹个浮层不换码"就得改这条，属于行为变更，交给用户决定。
   副作用是"配对页为第一层时按 MENU 弹退出确认、再取消"也会换一张码 ——
   那一路只在"无已配对设备 + 已退到根"时走得到，且用户本来就在往外走。
2. **`goFatal()` 仍落主界面显示无线电错误**：那是失败面板（`[确定键] 重试`），
   不是正常主界面，与"无设备不回主界面"那条铁律不冲突（STATUS 里早已记为例外）。

# 同日补充：铁律收口 + "更加底层"的重做

用户看过头一版后给了六条直接指示，并指出方法上的问题：

> 你的界面层级逻辑写的过于死板…… 你应该理解其中更加底层的界面逻辑 你只死板的把"此界面
> 此操作应该干什么"写进程序是不够的 如果用户做出了你没有预料到的操作呢？

这句话是对的，而且指出的是**头一版的做法**：我把"没设备不许进主界面"写在三个调用点上、
把"上一级是谁"写在按键分支里 —— 那是"此界面此操作应该干什么"的清单，少写一处就漏一处。
这一版的原则改成：**规则写在唯一的收口处，从状态推行为，不列行为清单**。

## 一、两条铁律的守卫搬进 showScreen（唯一的切屏口）

```java
if (target == SCR_MAIN && !hasPairedDevice())  target = SCR_PAIRING;   // ① 主界面这一态根本不存在
if (target == SCR_PAIRING && !hasPairedDevice() && …) { promptPairingRequired(); return; }  // ② 进配对页必经提示
```

- ①**"没有已配对设备时严禁进入正常主界面"**（用户原话）从此与调用方**无关**：谁想切过去
  都会被改成配对流程。以前 landAfterModeChoice / beginModeSwitch 完成回调 / goBackOneLevel
  各写一遍，用户实测报的那条"菜单里换连接方式 → 一台设备都没有却直接进了主界面"就是漏了一处。
- ②进配对页的那道门同理，只剩 `enterPairingHome()`（应用把配对页**立成家**）与
  `pairingFlowVisited()`（用户**已经在配对流程里**）两种放行。

**"配对流程里"怎么判**（这一条是从"提示的用途"推出来的，不是拍的）：提示的用途是
**在掉进"这台机器还没配对过手机"这一态时告诉用户一声**。所以：

| 场景 | 提示？ | 为什么 |
|---|---|---|
| 首启选完连接方式 / 无设备开机 | **弹** | 用户是刚从别处掉进这一态的 |
| 把最后一台手机解除绑定后往回收 | **弹** | 同上（层级历史里没有配对页） |
| 配对页 → 垃圾桶 → 菜单 → MENU 返回 | 不弹 | 用户自己走进来的，从它的菜单绕一圈回来还要再确认一次只是噪声 |
| 配对页上关掉一条提示 | 不弹 | 那是关浮层、回到原屏，不是"进配对页" |

## 二、MENU 在配对页的两种语义 —— 由"谁把用户带进来的"决定

用户定版两条：

> 如果是处于首次启动软件自动要求进入的配对模式之下 那么在此种配对界面中 menu键功能应为退出软件
> 如果是用户手动在菜单中点击进入配对模式进入的配对模式 那么在此种配对模式界面中 menu键功能应为返回刚才显示的界面

落到实现上**没有加任何新判断**，是层级历史自然给出的：**应用自动进的那一支 = 把配对页立成家
（`enterPairingHome()` → 历史清零）→ 没有上一级 → MENU = 退出软件；用户自己从菜单进的那一支 =
普通入栈 → 有上一级 → MENU = 返回。** 两条都来自同一条规则（"第一层 = 退出"）。

底栏提示也随之变（用户要求"menu键的功能不同时下方的提示栏提示也应随之变化"）：
`refreshMenuHint()` 用**同一个判据**（`navHistory.isEmpty()`）切"MENU 后面那块"是返回箭头
还是"退出"两个字（图标字体的私有区没有汉字，所以是**两个控件切可见性**，不是换字面）。
连接设置面板同理 —— 首启它就是第一层，底栏写"退出"才是实话。

## 三、配对模式下的菜单：隐藏"进入配对模式"

菜单回到**两份模型**（用户要求）：{标题, 当前值, **动作码**}，配对模式那一份藏着
"进入配对模式"。两项保护写在这里：

1. **按动作码分发，不按下标** —— 两份模型项数不同（5 项 / 4 项），下标会错位；
   "刷菜单值"（连接方式、已配对台数）也按动作码找行，不写死下标。
2. **哪一份由"菜单是从哪一屏打开的"决定**（`menuFromPairing`），而那一态**必然**是
   "没有已配对设备或用户自己走进了配对页"。顺带说明：这不是换装那版被我删掉的
   "精简菜单"（那是另一套项：连接模式选择/Wi-Fi 设置/关于/退出），这一份只藏一项。

## 四、先弹"请选择连接方式"，确定之后才是选择界面（用户要求）

`onResume` 里 `savedMode == null` 变成：**先把连接设置面板立起来，再把提示盖上去**
（`showScreen(SCR_MODE)` + `promptModeChoice()`）。为什么让面板在浮层底下而不是黑屏：
本工程所有浮层都是"悬在下层之上、透出下层"的原厂做法，而且关掉提示时看到的就是
"我刚才要选连接方式那一屏"。配对提示的按钮同时按用户要求从"进入配对模式"改成**"确定"**
（它是告知 + 确认，不是"点这里开始配对"那种动作按钮）。

## 五、弹窗的按键提示栏与正常状态同高（用户指出）

原厂对话框那份 `p_footer` 是 **640×60 @y420**，比其余各屏的底栏（`bg_footer52` 640×52 @y428）
高 8px 也上移 8px —— 用户一眼就看出"弹窗的提示栏被加高了"。现在改成与其余各屏**逐项相同**
（同素材、同高、同 paddingRight）。面板随之从 416 长到 **424**（y428 与底栏严丝合缝）：
素材是平图，纵向拉 8px（2%）看不出来，而文字/按钮的 y 都是相对面板顶部的，一个都没动。
（`tools/ui/mk_ui_preview.py` 的结构自检"各屏子 View 高度合计 = 480"当场拦下了这一改 ——
它正是为这类"底栏浮起来"踩的坑写的。）

## 六、顺手改掉的两处"靠副作用"的实现

1. **配对窗不再因为"配对页上弹了浮层"而被关掉**：原来 `showScreen` 的判据是"目标屏号不是
   配对页就关窗"，浮层也算 —— 于是启动时那条配对提示一弹一关就白白换了一张码（用户会看到
   码自己变了）。现在只有**真的离开配对页到别的屏**才关窗，而"配对码连错 5 次自动换新码"
   改成在 `onPairingAttemptFailed` 里**显式**换（提示的字面就是"已自动更换新的配对码"，
   那就真在弹提示之前换掉）—— 功能该在哪儿发生就写在哪儿。
2. **`goFatal()` 不再强拉主界面**：老写法是"启动失败 → 把界面拉回主界面看错误"，现在两处
   都不成立：① 无已配对设备时主界面根本不该出现（铁律）；② 拉过去也未必停在"服务状态"块上。
   改成**不换屏**、把当前屏的正文块切到"服务状态"（两块正文本来就是同一份文本），
