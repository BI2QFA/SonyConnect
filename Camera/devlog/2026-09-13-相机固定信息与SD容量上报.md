### 用固件镜像把真值钉死

先把"到底该是什么值"定死再写代码。本机固件里这份数据是 **nflasha2 分区的一个文件**：

```
extracted/dump/nflasha2_unpacked/Backup.bin    881121 字节
  偏移 0x0C = "BK4"          ← 正是 Backup_check_header() 校验的那个头
  偏移 0xC0 = "CX79101_CN2"  ← 正是 Tweak 显示的「Backup region」
```

而且 `drivers/backup_senser.h` 里连字段都标好了：
`char region[0x20]; // data[0xC0:0xE0]`；`api/tweaks.cpp` 里也印证了格式 ——
`strchr(region, '_')` 必须找到下划线，然后拿 `_` **后半段**去查 `langs_map`
（键就是 `CN2`/`AP2`/`IN5`…）。同目录 `0110_backup/MainDest.txt` 写的
`CX79100_UC2.bin`、以及 `CX79101_CN2.bin` / `CX79101_AP2.bin` 那一堆出货目标文件，
都说明这个串就是"机型码_地区码"。

★ 用户看到的 `cx79101_cn2` 是**小写打的**，镜像里的字节是大写 `CX79101_CN2`
（Tweak 那侧也是原样 `NewStringUTF`，不会改大小写）。

★ 顺带确认：`nflasha2` 里有 `updater/dat4`，而平台读固件版本用的是
`/setting/updater/dat4` —— 所以该分区在相机上挂作 `/setting`。**但 Tweak 并不读文件**，
它走的是 uIPC 消息（下面）。

### 最终实现：照抄 Tweak（原生路）

```
NativeInfo.region()  [Java]
  → Java_com_bi2qfa_sonyconnect_NativeInfo_region  [native/sonyinfo.c]
  → backup_senser_cmd_preset_data_read(1, buf, 0x100000)   [native/backup_senser.c]
  → osal_valloc_msg_wait / osal_snd_sync_msg / osal_free_msg  [UND，运行时由
                                  相机 /system/lib/libosal_uipc.so 真库解析]
  → 校验 buf[0x0C] ∈ {"BK2","BK4"} → 取 buf[0xC0] 的串
```

渠道是 OSAL 消息 **BACKUP_SENSER = 0x3E0166**、功能号 5、模式 1（从对面内存读）。
preset data 有 881121 字节，远超 OSAL 消息 0x130 字节的内联缓冲，所以对面回的是
**指针**（`msg.res_ptr`），由 `native/mem.c` 按页对齐 `mmap("/dev/mem")` 取回 ——
**读这条路最终依赖 `/dev/mem` 可读**。Tweak 在这台机器上能取到值，说明它是可读的。

`backup_senser.c` / `mem.c` 是 OpenMemories-Platform `drivers/` 下同名文件的移植
（只保留只读分支：写分支、以及 `#ifndef MODE_ANDROID` 里那两条被平台自己在
Android 模式禁掉的 `preset_data_status` / `version` 都没搬）。消息结构体
（`type/err/data_len/res_ptr/res_len` + 0x130 联合体）必须**逐字段一致** ——
那是与 BIONZ 侧约定的 ABI。

`native/backup.c`（型号/序列号那条 BACKUP=0x3E014D 的通道）和 `native/osal_uipc.S`
（把三个 OSAL 符号做成 UND 的空 stub）本来就在工程里，这次直接复用。

### 为什么先判"走不通"又走通了

第一版判断的依据是：
① 这是 native（uIPC + `/dev/mem`），纯 Java 无路；
② 本工程**历史上真的做过这件事**并失败过 —— `devlog/2026-09-06.md`：
"libsonyinfo 原生调用在该机上带崩整个进程"，两次进程隔离（`Runtime.exec` 起
`dalvikvm`、`:info` 独立进程）也都被相机的进程组策略杀掉，最后的处置是
**删掉 .so 走纯 Java**。

用户仍要求走 Tweak 路线，于是照做，并针对当年那个嫌疑做了防护：
当年怀疑是"Backup 属性填充垃圾字节触发 `NewStringUTF` abort"，所以这次
**返回前逐字节清洗为可打印 ASCII、按 0x20 字段边界读、遇 NUL 即止**
（`clean_jstring`，本来就写在该文件里），Java 侧整条 `try/catch(Throwable)`。

★ 必须说清的边界：`try/catch` 挡得住 Java 层异常（`UnsatisfiedLinkError` 等），
**挡不住原生段错误**。如果原生侧真的崩，进程还是会没。触发点和当年一样
（连接时拉 DEVICE_INFO，或关于页），这一点在「未验证」一节里写明。

## 三、Java API 版本 = `version.platform`

键名与"整串下发"的决定都取自 OpenMemories-Framework 的
`DeviceInfo.CameraDeviceInfo`：

```java
private String[] getPlatform() {
    String[] platform = getString(ScalarProperties.PROP_VERSION_PLATFORM).split("\\.");
    if (platform.length != 2) throw new RuntimeException("Platform property has wrong format");
    return platform;
}
public int getHardwareVersion() { return Integer.parseInt(getPlatform()[0]); }  // "2.3" → 2
public int getApiVersion()      { return Integer.parseInt(getPlatform()[1]); }  // "2.3" → 3
```

也就是说这个属性是 `"硬件版本.API版本"` 两段。**但本工程整串下发、不自己劈**：
Tweak 里标注为 "Java API version" 的那个 backup 属性（id `0x01660024`，8 字节）
本来就是**一整串**，劈开只是 Framework 自己的解读。手机端展示的就是这一串
（`2.3`），要拆再说 —— 少一层自作聪明就少一个错处。

## 四、SD 容量

```java
private static long[] sdUsage(File root) {
    long total = root.getTotalSpace();
    long free  = root.getFreeSpace();
    if (free <= 0) free = root.getUsableSpace();
    if (total <= 0 || total > 4398046511104L) return {-1, -1};  // 4 TiB
    if (free < 0 || free > total) free = 0;
    return {total, total - free};
}
```

三个决定，都有理由：

1. **不缓存**（与型号/地区那些"读一次存下来"的相反）。容量是会变的量：
   用户中途换卡、边拍边填。`getRootDir()` 每次调用都重新解析挂载点，
   缓存下来就会出现"换了卡容量还是旧卡的"。
   （手机端每个会话只拉一次 `DEVICE_INFO`，本来就是快照语义，不必再缓存。）
2. **空闲优先 `getFreeSpace()`**，不用 `getUsableSpace()`：后者是"本进程还能写多少"，
   在相机的 FUSE 挂载上会偏小，算出来的"已用"虚高。文件管理器口径才是用户预期。
3. **合理性拦截**：`total<=0` 或 `>4TiB` 一律判读不到。
   相机上 `getRootDir()` 有时会落到一个**存在但不是挂载点**的空目录，
   这时 statfs 报的是**父文件系统**的大小 ——看着像真值其实是错的。
   宁可返回 `-1` 让手机端显示 "—"，也不显示一个假容量。

★ `File.getTotalSpace()`/`getFreeSpace()` 是 API 9+（Java 6）的东西，
本机 compileSdk 15 / 源码级 1.6 都在范围内，不需要 `StatFs`。
