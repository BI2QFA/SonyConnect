# 传输完成后"目录读取失败"并自动断开 — 根因与修复

**症状**（用户真机复现，手机端 adb logcat 取证）：一批文件传完，回到文件页立刻显示
**"目录读取失败"**，过一会儿（约 10 秒）连接**自动断开**。

**结论**：不是相机断的，也不是心跳抖的 —— 是**手机端自己在批次结束时把相机会话关了**。
`DownloadService` 收尾里的 `ObjectRepository.closeAll()` 是 FTP 时代的遗留。

---

## 一、logcat 证据链

失败窗口（相机 `192.168.31.25`，Wi-Fi 客户端模式）：

```
22:20:08.057  ActivityManager: Background started FGS … DownloadService     ← 批次跑完、服务收尾
22:20:20.824  ObjectRepository: list failed: java.io.IOException: 未连接相机 192.168.31.25
22:20:20.826  FilesScreen:      目录读取失败: 目录读取失败
22:20:23.408  ObjectRepository: ping failed: java.io.IOException: 未连接相机 192.168.31.25
22:20:24.951  … list failed / 26.413 ping failed / 29.416 ping failed …
22:20:29.562  Discovery: 扫描完成：已知 1 条，命中 1 台        ← 状态机已回到未连接，自动扫描重开
```

三个关键点：

1. `未连接相机 <ip>` 只由 `ObjectRepository.requireClient()` 抛出 —— 含义是
   `sessions[host]` 已经不在了，即 `PtpIpClient` 被**关闭**过（不是网络断，也不是相机拒）。
2. 失败从"批次收尾"之后**才开始**：批次期间（22:14:45 → 22:20:08）协议层一行日志都没有。
3. 心跳是 3 秒一次、连失 3 次才断（`HEARTBEAT_MAX_MISSES = 3`）：`22:20:23 / 26 / 29`
   正好是三次失联，`22:20:29` 的重新扫描就是 `ConnectionCenter.disconnect("失去与相机的连接")`
   之后的必然结果 —— **"过一会自动断开"是心跳在给一个已经死掉的会话收尸**。

同一份日志里还有一处被误读过的签名：

```
22:14:36.281  list failed: com.bi2qfa.sonyconnect.ptpip.PtpProtocolException: 相机回错误码 0x2003
```

`0x2003`（`RC_SESSION_NOT_OPEN`）**不是相机回的**，是 `PtpIpClient.close()` 为了唤醒挂起事务
自己塞进去的码（`close()` 里 `val code = PtpCodec.RC_SESSION_NOT_OPEN`）。它把"本端关了连接"
伪装成"相机回错误码"，排障时会把方向指错。已一并改掉（见修复 B）。

## 二、根因

`transfer/DownloadService.kt` 的 `drainSafely()` 收尾：

```kotlin
} finally {
    …
    TransferStore.markBatchEnded()
    ObjectRepository.closeAll()   // ← 把 sessions 里所有相机连接全部关掉
    runningFlag.set(false)
    stopSelf()
}
```

类文档里它还被当成铁律写着：*"铁律对应物：停止/结束时 closeAll 关闭全部相机会话后 stopSelf"*。

那是 **FTP 时代的语义**：FTP 会话是有状态的、必须显式释放（相机端 FTP 服务会占着 SD 与
无线电），所以"传完就关"是对的。PTP/IP 下控制连接是**常驻会话**，它的生死由
`ConnectionCenter` 一处裁决（心跳保活、断开收尾、退出链、缩略图批次都挂在上面），
DownloadService 只是个批次执行者，没有资格收走用户的会话。

于是链路变成：批次结束 → `closeAll()` → 用户回到文件页 → `requireClient` 抛
`未连接相机` → FilesScreen 显示"目录读取失败" → 心跳连失三次 → 自动断开。

顺带把 `ConnectionCenter.disconnect()` 加了日志（`disconnect: <原因>`）：此前自动断开
**一行日志都没有**，"过一会自动断开"只能靠猜，这次排障就吃了这个亏。

## 三、修复

### A. 批次结束不再关会话（根因）

`DownloadService` 收尾删掉 `ObjectRepository.closeAll()`，类文档改写成"会话语义"说明，
写清**为什么不能关**（防止后人再按 FTP 直觉加回来）。批次开始/结束仍各发一个
缩略图队列 PAUSE / RESUME，这是它对相机唯一该做的动作。

### B. 本地唤醒不再冒充相机错误码

`PtpIpClient.close()` 唤醒挂起事务改用**本地哨兵码**（`CODE_LOCAL_CLOSED = -1`，
负数，故意不落在任何 PTP 码空间里），`checkOk()` 见到它就报
`连接已关闭，未收到相机应答`，不再出现"相机回错误码 0x2003"这种指向相机的假消息。

### C. 配对死循环（同一份日志里的第二个真问题）

同一份日志开头，用户在 22:12:00–22:12:49 之间**连续 6 次**配对失败：

```
ObjectRepository: pair failed: PairingFailedException 配对被拒绝（0x2005）
```

`0x2005 = RC_NOT_SUPPORTED`。相机端只有在**会话已获准**（`serveControl` 的准入早已通过、
即本机设备码就在相机配对表里）时才会走到 `dispatchData` 里那条
`PAIR_* → RC_NOT_SUPPORTED`。所以这个码的真实含义是：

> **相机认识我，我不认识相机** —— 相机侧记录还在，手机侧记录丢了
> （清过数据 / 换过机 / **在未连接时点过"解除配对"**：那条路径的 `pairRemove` 要求
> 当前正连着该相机，所以相机侧那条记录被留了下来）。

原先的行为是个**死循环**：本地无记录 → UI 强制配对 → 相机拒绝配对 → 只能跑去相机菜单
删记录。而且报错文案（"配对码不正确，或相机未开启配对模式"）是**假的** —— 那个码相机根本
没看。

改法（手机端单侧，相机端一行未动）：

- `PairingClient.run()`：`PAIR_BEGIN` 收到 `RC_NOT_SUPPORTED` 时不再当失败，返回
  `Result(alreadyPaired = true)`（不进入第二步验码 —— 相机没看那个码）。
- `PtpIpClient.pairAndConnect()` 返回 `Boolean`（true = 相机按码确认了；false = 相机早就认识本机）。
- `ObjectRepository.pair()` 返回三态 `PairOutcome{FAILED, PAIRED, ALREADY_PAIRED}`。
- `ConnectionCenter.submitPairCode()`：`ALREADY_PAIRED` 照常补本地记录并进入已连接，
  其余步骤与正常配对逐字相同。

**这没有削弱强制配对**：准入那道门完全没动，相机仍然只放行配对表里的设备码；
变的只是手机端把自己的本地记录补齐到与相机一致。相机若真不认识本机，走的是
`Init Fail(NOT_PAIRED)`，在这条路径之外。

## 四、验证

- **A**：`javap -c` 反汇编本次构建产物里的 `DownloadService.class` —— `closeAll` 出现
  **0 次**，`thumbQueue`(4) / `exitApp`(1) / `stopSelf`(3) 均在。构建产物内 `dex` 字节级
  检索也确认 B、C 的新字符串已进包（`连接已关闭，未收到相机应答`、`相机已认识本机，改为补齐本地配对记录`）。
- **C 的相机侧前提**：桌面回归里已有断言 `PAIR_BEGIN 在 P1 回 NOT_SUPPORTED`（在**已获准会话**
  上发 `PAIR_BEGIN`）—— 修复依赖的相机契约本就是绿的，相机端**本次一行未改**。
- 手机端 `:app:assembleDebug` 通过；`versionCode=2 / versionName=1.0`，签名与已发布 1.0 一致。

## 五、待真机复验

1. 传一批文件 → 返回文件页：**目录应正常刷新**，连接保持；心跳继续（电量/镜头仍刷新）。
2. 传完后 30 秒内不进任何页面，连接**不应**自动断开。
3. 手机端"解除配对"（**未连接状态下也试一次**）→ 重新配对：应能直接连上而不是卡在
   "配对失败"（走 `ALREADY_PAIRED` 补记录路径）。
4. 备注：手机端记录丢失、相机仍有记录时，**配对码不再被核对**（相机把请求当协议错用回绝），
   手机端会直接连上。这是有意为之的自愈行为 —— 若测试"错码被拒"，请先确保两端都无记录
   （或在相机上先解除配对）。
