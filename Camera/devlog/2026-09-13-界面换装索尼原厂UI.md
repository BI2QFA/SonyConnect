# 相机端界面换装索尼原厂 UI（2026-09-13）

依据 `SonyUI复刻包`（ILCE-6300 固件解包，36.9 万行分析文档 + 8038 张原厂素材）把相机端
从"自画近似值"换成**原厂素材 + 原厂真值几何**。主界面按用户给的排版示例图重排。

## 一、总原则：只动皮肤层

| 不动 | 说明 |
|---|---|
| `PtpIpServer` / `PtpCameraHandler` / `PairingStore` / `RadioWrapper` | 业务一行未改 |
| `showScreen(SCR_*)` 骨架 | 屏幕常量、可见性切换、按键分发全保留 |
| `ScalarInput.ISV_KEY_*` 分发 | `onKeyDown` 的 switch(scanCode) 只加了两个 case（见下） |
| 六条退出链 | 退出路径完全没碰 |

改动集中在：素材、`styles.xml`/`colors.xml`、各屏几何、底部按键引导，以及主界面
新增的"两按钮 + 三块正文"交互。

## 五、9-patch：本轮最大的坑（AAPT2 会直接拒收固件原图）

固件的 `*.9.png` marker 是 #DD7700、四角还不透明，AAPT2 报
`top-left corner pixel must be either opaque white or transparent`。实测
`p_16_dd_parts_43_set_background_menu3rdlayer.9.png` 有 **803 个非法边框像素**。

- 新增 `tools/ui/patch9.py`（check / rebuild）：按资源包 `mk_lite_patch9.py` 的重建法
  —— 原图整体贴 (1,1)、外圈只在可拉伸段画纯黑 marker、**四角保持透明**。
- SetMenu 面板重建时**必须把两条标题线留在固定区**：那张 516×160 的图在 y=23 和 y=80
  各有一条横线（第一条是 #DD7700 系亮线、第二条是 #C8C8C8 细线），第一版把拉伸段取成
  y 30..130 把第二条线一起拉了 → 预览里面板中间横着一条亮线。改成 `--sy 85,130`
  （只拉两条线之间的纯黑段）后干净了。
- 其余 9-patch 直接用 `SonyUIDemoLite` 里**已重建且实机验证过**的那套
  （`row_focus` / `s82_focus` / `btn_focus` / `btn_normal`），实测四角透明、marker 合法。

## 六、先出预览再动工程（并在这个环节抓到三个真 bug）

`tools/ui/mk_ui_preview.py`：用**同一批素材 + 同一批几何常量**合成 640×480 的 13 张预览
（含 9-patch 的真实 marker 拉伸算法与 textScaleX 0.7001 的文字压缩），输出到
`tools/ui/preview/`（`_总览.png` 是一张全览图）。这一步的价值立刻兑现了：

1. **配对页文字变豆腐块**：`text()` 原来是"按每段首字符选字面"，而" 已配对"这段的首字符
   是空格 → 整段落到拉丁字面（UniversOTS 没有中日韩字形）→ 方块。改成**逐字符判定、
   空格跟着前一个字面走**；顺带把各段改成**同一基线**拼接（原本按各自 bbox 下沿对齐会错位）。
2. **`s82_focus.9` 被误判**：拉伸出来是"金色渐变 + 中间黑疙瘩"，一度以为素材坏了 ——
   放大看原图才明白它就是**一圈发光描边框**（原厂 ListMenu 的选中样式），虚惊一场。
3. **主界面服务状态会钻到按钮底下**：写完布局自检时发现 6 行状态文字（38px）会越过
   y=266 的按钮行 → 状态块改 32px（`FontSize.MS`，原厂列表标签档）+ 高度收到 250px。

PIL 里另外两个坑：`fill` 必须给元组（给整数会被当打包色值，二维码画出来是红的）；
PNG 里的透明区在合成时要给 mask。

## 七、构建配置

- 新增 `aaptOptions { cruncherEnabled = false }`：PNG 优化器不碰素材，9-patch 的 marker

## 八、三条编码铁律（资源包错误记录 #10/#11 的教训，本轮全程遵守）

1. 字号一律 px（`setTextSize(COMPLEX_UNIT_PX, n)` / XML 里写 `42px`），**绝不用 sp**
2. 横向压缩用 `android:textScaleX` / `TextView.setTextScaleX`，**绝不用 `View.setScaleX`**
   （后者绕 View 中心缩放整个视图，右对齐的文字会整体漂移）
3. 带行距的 `PFontSize` 族**只能用在容器高 ≥60px 的地方**：`lineSpacingExtra` 对单行也生效，
   42px 字 + 10px 行距 ≈ 54px，塞进 49px 的菜单行 / 56px 的按钮会被裁 → 另立 `PfT*` 紧凑族
   （去行距 + 关 `includeFontPadding`）。DemoLite 的 `row_menu.xml`（606×49 + 42px +
   includeFontPadding=false）是这条规矩的原型，已实机验证。

## 九、连接设置弹窗：真机错位 / 粗白条 / 缺分割条 / 不悬浮 —— 三个根因

### ① 整块内容被推下去 85px：9-patch 的**隐式内边距**

真机首装回报"设置的弹窗是错位的"。拿手机拍的斜面照片反推（`tools/ui/measure_photo.py`
拟合面板四条边求交点做投影校正）得到：标题墨迹 29..76 → 120..160、列表首行 95..144 →
188..239，水平也 +6。`(+6, +85)` 正好是那张面板 9-patch 的**固定边框**尺寸。

原因：**AAPT2 在右下两条边框上找不到 padding marker 时，会拿"可拉伸区"当内容区**，
给宿主 View 加 `(6, 85, 6, 30)` 的内边距。我把面板当 RelativeLayout 的 background 用，
子节点就全被推下去 85px。查证手段：`tools/ui/dump_patch9_apk.py` 直接读编译产物的
npTc 块（字段顺序是实测反推的，padding 的顺序是 **L,R,T,B**）。

**解法：照抄原厂的写法。** dump 原厂 `com.sony.imaging.app.synctosmartphone-1` 的
`res/layout/menu_set.xml` 才发现 Sony 早就绕开了这件事：

```xml
RelativeLayout (根，background=#88000000 遮罩)
├── ImageView  id=menu_background  518×480 @x62  background=那张面板
│                                ← 只当装饰件，没有子节点
├── TextView   标题  46 高 @面板(13,29)，alignLeft/alignTop 贴到它
├── ItemAlignedListView  489×302 @面板(20,95) paddingRight 11 divider 2px
└── FooterGuide  500×40 @(70,413)
```

**"9-patch 只当装饰件、内容是它的兄弟节点"** 就是答案。行的选中图案同理：原厂
`menu_page_adapter.xml` / `menu_set_adapter.xml` 里焦点是行内一个 ImageView
（tag=`selectable_background`，src=`menu_list_selector`），**不是行的 background**。
两处都照做后，padding 与布局彻底解耦。

### ② "粗白条" + ③ "按键栏上方的分割条没了"：**同一个根因 —— 拉伸区圈进了内容行**

第二次真机回报两条症状：设置弹窗里横着一条**粗白条**，而且**按键提示栏上方那条分割线没了**。

从编译产物里读出**原厂那张面板的真实标记**（十六进制解 npTc）：

```
原厂 p_16_dd_parts_43_set_background_menu3rdlayer.9.png
    xDivs=(257, 258)  yDivs=(85, 86)     ← 只在正中留 1 像素可拉伸，其余 1:1 原样绘制
    我的 set_panel.9.png
    xDivs=(6, 510)    yDivs=(85, 130)    ← 拉伸区取了 46 行，问题出在这
```

那张素材在 x=258 的纵向剖面（只列有变化的行）——**一共四条线，不是三条**：

| 内容行 | 像素 | 是什么 | 原厂落点 |
|---|---|---|---|
| 22 | (221,221,221,135) | 标题带上边线 | 22（固定区，1:1） |
| 79 | (136,136,136,255) | 标题带下边线 | 79（固定区，1:1） |
| **89** | (136,136,136,255) | **列表上方那条分割线** | **409**（在 1 像素拉伸点之下，整体 +320） |
| 134 | (119,119,119,255) | 按键栏下方那条线 | 454 |

我把拉伸区取成内容 85..130，**把 89 行那条线一起圈进去拉成了 46→365 的粗灰带**
（就是"粗白条"）；同时它再也回不到 409，**按键栏上方那条分割线就没了**。
一个错误，两个症状。

**修法**：拉伸区挪到全黑的那段（内容 81..89，避开 22/79/89/134 四条线）。
重建后落点与原厂**逐像素一致**：22 / 79 / 409 / 454。

顺带记一条：`tools/ui/mk_ui_preview.py` 的 `patch()` 也有同一个 off-by-one ——
边框 marker 是**文件坐标**，内容图要去掉 1px 边框，行号得 **-1**（文件行 82..89 →
可拉伸的内容行 81..88）。漏掉它，预览里同样会把 89 行拉成粗带，于是"预览通过、真机报错"。

### ④ 弹窗要"悬浮在下方菜单之上"：`showScreen` 不该把下层收起来

原厂 `menu_set.xml` 的根就是一层 `#88000000` 遮罩 + 一块面板 —— 下层菜单**不收起来**，
透过遮罩还能看见（真机照片里弹窗左侧和下方就露着下层菜单的条目与它自己的按键引导）。

改为：`showScreen(SCR_MODE)` 时按**来路**把下层那一屏显出来压在下面
（从选项菜单进来留菜单、首启/清除后进主界面），其余目标照旧互斥显示。

## 十二、弹窗浮层化 + 字体钉死（用户："控件使用不对 / 字体和原厂不是一个"）

### ① 弹窗也要悬浮在下层之上

用户指出的"控件使用不对"：对话框后面不该是黑屏 —— 原版的确认框是**浮在下层之上**，
透过遮罩能看见后面的界面。原因同"连接设置"那一次：`showScreen` 把下层整屏收起来了。

改法统一：`showScreen` 里把**连接设置弹窗**与**三个对话框**都当作浮层 —— 浮层目标
**一个 base 屏都不动**（只切自己的可见性），非浮层目标照旧互斥显示。
这样对话框弹在哪儿（菜单上/配对页上/连接设置上）后面就露着那一屏，遮罩
（对话框 #66000000 / 设置 #88000000）负责压暗。

### ① 数据修复：先给结论，再说清"排除了什么"和"找到了什么"

**排除**：本 App 运行期**不写卡**。全量审计（`grep FileOutputStream|mkdir|renameTo|
delete` 全部源码）只有两处写入 —— ① `PairingStore` 的 `pairings.json` /
`device_id.hex`，落在 `getFilesDir()`（**应用私有目录**，不是存储卡）；② socket 输出流。

所以"当前版本运行期在卡上留文件"这件事不成立。

**找到的真问题（两条，都在退出链上）**：

1. **历届版本的日志文件没被清干净**。`deleteTraceFiles()` 只删了
   `SONYCONNECT_LOG.TXT` 一个名字，而 devlog 2026-09-06 记着这条线上还写过
   `SonyConnect-trace.log`（v1.1 飞行记录仪）与 `SonyConnect-crash.log`（v1.0 崩溃日志），
   两个都在**卡根**，**任何版本都没删过**。相机把"卡根出现陌生文件"当作图像数据库
   失同步，下次开机就挂"正在修复数据"。→ 现在 `TRACE_NAMES` 收全三个名字，并对
   卡根做一次**非递归、只删文件、名字含 sonyconnect** 的兜底扫描（`/sdcard` 等三个
   路径按 canonical path 去重，只扫一次）。目录与照片不可能被误伤。

2. **退出时可能有连接线程正握着 SD 句柄就被收掉**（这条更可能是主因）。
   `ThumbPrefetcher.stop()` 原先只 `interrupt()`、**不 join**；`PtpIpServer.stop()`
   也只 `socket.close()`、**不 join 连接线程**。而连接线程读照片/缩略图时
   `RandomAccessFile` 是"读完这一轮才在 finally 关"，socket 关掉只是让下一次收发
   抛异常。退出链最后一句 `DAConnectionManager.finish()` 一执行，进程就没了 ——
   正好卡在那个窗口，卡上就留一个没归位的占用。→ 两处都加**有上限的 join**
   （预取器 2s；连接线程按连接数分摊 2s 总预算）。这与用户定的退出铁律
   （"释放 sd 卡占用…恢复到正常状态后才完全关闭软件"）是一致的，之前只是没做到。
   另外 `PtpIpServer` 新增 `dropAllConnections()`（只断会话、不停服务器），给②用。

> 注：`SonyConnect-交接文档` 与更早的 SonyFTP 记录里，这个问题被定性为
> "固件承受不住热点完整拆除→立即重建的硬件级循环"（无法从代码层证实）。这次能把
> "应用层到底有没有留东西"这条彻底证伪/证实：**应用层不留文件，但句柄可能没等干净** ——
> 后者是可修的，现在就修了。真机上如果还出现，那就只剩固件时序那一种解释了。

## 十七、主界面不实时刷新（用户实测）+ 两处设备码上屏

### ① 主界面状态不实时刷新 —— 心跳只驱动了状态文字，没驱动图标那一块

用户报："相机端停在主界面，手机断开连接，主界面的设备型号并不会变成未连接、
手机图标也不会熄灭，必须进入一个别的界面之后才会刷新。"

病根在 `mainTicker`（1s 心跳）里：

```java
if (screen == SCR_MAIN) {
    String now = buildMainStatusText();
    if (!now.equals(lastMainStatus)) {          // 只比状态文字
        lastMainStatus = now;
        statusView.setText(now);
        updateQrCode();
    }
}
```

它**只**在状态文字变化时 `setText`。而"手机图标 on/off、中间六个点、图标下那行
型号（`mainCapRight`）"全都只由 `refreshMainScreen()` 刷 —— 那个方法只在
**切屏**（`showScreen(SCR_MAIN)`）、配对成功、按键切正文块这三个时刻被调。
于是手机一断：若停在"服务状态"块，文字会变；但图标还亮着、型号还写着，
**必须离开主界面再回来**才更新。用户看到的就是这个。

修法不是"每秒无条件调 `refreshMainScreen()`" —— 它末尾会 `updateQrCode()`，
每秒重渲一次二维码位图，白烧相机那点 CPU（这正是当初写成"文字没变就不碰视图"的原因）。
改成**轮询连接状态快照、变了才整块刷**：

```java
String caption = phoneModelText();                    // "未连接" / 型号名 / "已连接"
boolean linkChanged = lastPhoneCaption == null || !lastPhoneCaption.equals(caption);
if (textChanged) { lastMainStatus = now; statusView.setText(now); }
if (linkChanged) { lastPhoneCaption = caption; refreshMainScreen(); }  // 内含一次 updateQrCode
else if (textChanged) { updateQrCode(); }
```

`phoneModelText()` 同时编码了"有没有连着"和"连的是谁"，所以拿它当快照就够。
连接状态是**外部事实**（TCP 建连/断开），相机端没有回调可挂，只能靠这个心跳发现 ——
心跳就必须驱动整块主屏，不能只驱动状态文字。

> 附带确认过断开是怎么被发现的：手机正常退出会关 socket，连接线程读到 EOF 立刻
> `close()` 并从 `conns` 摘掉，1s 内计数就归零；手机被强杀/无线掉线那种情况靠
> `CONTROL_IDLE_MS`（20s 读超时）兜底，属既有设计。

### ② 关于页加"本机设备码"

第三行 `本机设备码：<16 位小写 hex>`，取的就是配对表落盘的 `device_id.hex`
（`pairingStore.deviceIdHex()`）—— **原样显示、不改大小写**，因为手机端也按小写
归一（`IdentityRepo.kt` 里 `deviceId = hex.lowercase()`），用户拿它对手机端是逐字符
对得上的。进屏时由 `updateAboutText()` 填一次（设备码随机生成一次后永不变）。
布局 XML 里的 `android:text` 保留一份带样例码的三行默认值，只为让布局预览不少一行；
真机进屏时整段被替换。

顶上那颗电池图标本身又是 #DDDDDD —— 文字跟图标同色才是一套。改成 `PfT28`
（同字号同 textScaleX 0.7199，只把颜色换成 `font_normal`），`PfT28D` 顺手删掉
（全工程只有它一个引用）。预览的 `header_app()` 也同步从 C_DIS 改 C_TEXT。

### ② 设备码只显示前 8 位

用户定版：前 8 位（4 字节）区分"同一台相机配过的几台手机"足够，字数和行宽也舒服。
新增 `MainActivity.shortCode()`，**只在显示这一层截断** —— 协议比较、配对表主键、
落盘文件里一律仍是完整 16 位（别把截断带进数据层）。关于页与已配对设备页值列都走它。

### ③ "两个设备码一样"的根因：手机端握手 GUID 传的是相机的码

用户问"为什么本机设备码和手机设备码是一样的"。查下来**不是相机端的问题**：

PTP/IP `Init Command Request` 的 GUID 字段语义是"**发起方（手机）是谁**"。
相机端就照这个语义用它 —— `Conn.deviceId = first.body[0..16]`，
`shortId()` 取前 8 字节 → 配对表主键 `peerDeviceId`、准入判定
`allowInitiator()/isDevicePaired()`（两者都是 `pairing.contains(guid8)`）、
单客户端 `evictOrReject()` 全用这一个值。

而手机端一直填的是**相机**的 GUID：`ConnectionCenter` 把探测应答里学到的
`cam.cameraGuid16`（`Discovery.kt:218 ← pr.guid`）当自己的身份传下去。
`IdentityRepo.guid16()`（本机 8B deviceId 补零，注释本来写得完全对）
只在 `Discovery.kt:105` 发探测请求时用过一次，握手这条路从没用过。
于是相机如实记下"这台手机的设备码 = 相机自己的设备码"，两处显示当然一样。

**影响不止显示重复**（这条要说清楚，比显示问题重）：

1. 配对表键恒等于相机自己的设备码 → 所有手机共用一键，`upsert` 互相覆盖，
   无论配过几台手机，表里永远只有一行；
2. 相机的设备码是**公开发放**的（UDP 探测应答与 Init Command Ack 都带着它，
   不需要配对就能拿到）→ 只要相机配对过任何一台手机，同网段任何人把这个码
   填进那个字段，就会被 `allowInitiator()` 当成"已配对设备"放行，
   **6 位配对码这道门被完全绕过**。去加密之后配对表是唯一准入依据，这条就更有分量。

**改的是手机端**（4 处，只改"发起方 GUID"这个参数）：`ConnectionCenter.kt` 的
`connect()`/`pair()` 调用、`ObjectRepository.kt` 里两处 `DataChannel(...)`，
全部 `cam.cameraGuid16` / `client.cameraGuid16` → `IdentityRepo.guid16()`。
数据通道也必须一起改 —— 相机端 `serveFile()` 会拿 DATA_OPEN 里的 GUID 比对令牌
绑定值、并按它找回**已获准的控制会话**，控制连接与数据通道必须是同一个值。
相机身份（从 Init Command Ack 学回来的 `cameraGuid16`）继续用于本地配对表键、
存储目录、界面显示，一处没动。两个参数的文档都补了⚠️，写明语义与"别传相机的码"。

**验收代价**：相机里现存记录是用"相机设备码"当键存的，改完后相机会回 `NOT_PAIRED`，
手机端自动清本地旧记录并提示重新配对 —— 每台已配对手机要**再输一次配对码**，属预期。

## 二十、关机自动启动（拨杆接管）+ 设置开关（vc23）

机制来源：`6300fw/docs/同步到智能手机-关机自动传输机制全解.md`（+ 同目录
`replica-autosync/` 参考实现）。核心结论复述一遍，因为后面所有设计都压在它上面：

```
拨杆 OFF → DIADEM 通知 DAConnectionManagerService：onChange(state=2, function="suspend")
        → 服务 queryIntentActivities(LAUNCH_ACTIVITY_ON_SUSPEND).get(0)   ← 按 priority 降序只取第一个
        → startActivity(认领者, extra: param_off_factor="OFF_BY_KEY")
        → 认领者只要不调 DAConnectionManager.finish()，相机就不断电（DIADEM 一直等）
        → 认领者调 finish() → 黑屏 launcher → 结束 Activity → 杀进程 → 广播 ExitCompleted → 切电
```

索尼原版「同步到智能手机」的这条 filter **priority=0**，所以我们写 10 就排在它前面，这次
关机由我们接管（**互斥**：`get(0)` 只有一个，原版的自动传输不会再被拉起）。

### 需求（用户原话，含一处必须先问清的冲突）

> 仿照这个做一个关机自动启动软件功能 在设置里放上功能开关／当这个功能关闭时 软件应该执行
> 另一套逻辑／当软件正在运行时拨动关机拨杆 屏幕不应该熄灭 应该自动进入软件的关闭流程彻底
> 关闭软件然后关机／此功能仅当软件运行时生效 退出软件时应同步关闭此功能／如果关机自动启动
> 软件功能打开 则在关机时自动按正常方式启动软件

第 5 条与第 6 条**互相冲突**（"仅当软件运行时生效、退出即关闭" vs "开关打开时关机就自动启动
软件" —— 后者恰恰要求软件**没运行**时接管权还在），所以先问了两个问题，用户定版：

1. **软件没运行 + 开关开着 → 自动启动我们的软件**（相机保持不断电，用户退出软件时才断电）。
2. **开关关着但软件正在运行 → 照旧不熄屏走关闭流程**（开关只管"没运行时要不要被拉起来"）。

于是三条行为定死：

| 情形 | 阀门组件 | 行为 |
|---|---|---|
| 软件运行中拨杆 | 装着 | 接管 → **不熄屏**走自己的关闭流程 → 彻底关闭 → 关机 |
| 软件没运行 + 开关开 | 装着 | **按正常方式启动软件**；相机不断电，用户退出软件时收尾关机 |
| 软件没运行 + 开关关 | 卸掉 | 我们压根不被解析到 → 相机普通关机（"另一套逻辑"） |

### 一个必须单独一个 Activity 的理由（本轮最容易踩的坑）

接管权要在运行期装/卸，而 `setComponentEnabledSetting(DISABLED)` 是**按组件整体**生效的 ——
把这条 filter 挂在 `MainActivity` 上，一"卸下接管权"就会连 `MAIN/LAUNCHER` 那条 filter
一起禁掉，**软件会从相机的应用菜单里消失**。所以阀门必须是独立的
`PowerOffGateActivity`，它只带着这一条 filter，装/卸都不动软件本体。

### 实现

**Manifest**：
- `MainActivity` 加 `android:launchMode="singleTask"` —— 软件被再次拉起（应用菜单点进来、
  或关机阀门把 extra 递过来）必须落到**同一个实例**上，否则会出现两个 Activity 各起一套
  无线电/服务（`onCreate` 里那串初始化只允许跑一次）。
- 新增 `PowerOffGateActivity`：`exported` + `screenOrientation=landscape` +
  `excludeFromRecents`，intent-filter `android:priority="10"`，主题与主界面同款纯黑无标题。
  **launchMode 用 standard（不是参考实现的 singleInstance）**：阀门是"转手就退场"的，
  退场后屏幕必须稳稳回到我们的界面（"屏幕不应该熄灭"）。同一个 task 里弹掉栈顶最可靠；
  另起一个 task 就得靠系统切回上一个 task。配合 `MainActivity` 的 singleTask 正好：
  阀门把 MainActivity 拉起来时，singleTask 语义会把压在它上面的阀门清掉。

**`PowerOffGateActivity`（新增，~150 行注释版）**只做转发，不画界面、**绝不调 `finish()`**：
① 软件活着 → `MainActivity.ownsPowerOff()` 交给它 → 自己退场；
② 软件没运行 + 开关开着 → `ACTION_MAIN + 显式类名 + NEW_TASK` 把 MainActivity 拉起来
（照抄系统服务拉起认领者的写法）→ 自己退场，**不交还关机权**；
③ 软件没运行 + 开关关着 → 只可能是"上次没干净退出没来得及卸阀门"，兜底立刻交还关机权。

**`MainActivity`**：
- `powerOffAutoOn`（prefs 键 `poweroff_auto`，**默认关**）+ 选项菜单新增
  「关机自动启动」项（值列 开/关，中键**就地切**并落盘，与"已配对设备"那类不同，
  不进二级页）。菜单由此 5 项变 6 项 —— 列表高从 302 收到 **304**
  （6×49 + 5×2），上边距 30→29 保持上下对称（29+304+29=362）。
- `gateArmed = setPowerOffGate(true)`：**运行期间一律装着**（与开关无关）。
- 退出链收尾 `disarmGateIfOff()`：开关关着就卸掉；开着则保持装着（"没运行时拨杆拉起软件"
  才成立）。`ExitCompletedReceiver`（切电前最后一班岗）里也补了一发同样的兜底。
- `onPause()` 选路 —— **本轮最关键的一处**：能走到 `onPause` 就说明是拨杆关机（另两条
  来路 `shuttingDown` / `jumpingToSystem` 已排除），于是按"阀门有没有装上"分岔：
  - **装上 → `beginOrderlyExit("正在关机···")`**：相机在等我们，走正规关闭流程
    （不熄屏 → 停服务 → 归位无线电 → 恢复 APO → `daFinishOnly()` 交还）。
  - 没装上 → 沿用 `runForcedExitCritical()` 竞速收尾（SonyFTP v1.2.3 的老办法）。

  ★ 这里有个**顺序陷阱**：`startActivity` 的时序是「先 onPause 旧 Activity，再 onCreate
  新 Activity」，所以**不能**用"阀门递过来的 extra 有没有到"当判据 —— 等到那时
  `onPause` 早跑完了。判据只能是"阀门装没装上"这个**在 onPause 之前就已知**的事实。
  ★ 也**不能**在 `onPause` 里做重活：它在 UI 线程上，同步等无线电沉降会把界面冻住，
  "正在关机···"的浮层根本画不出来。重活全在 `beginOrderlyExit` 起的后台线程里。

### 已知边界（照抄文档 §4.3 的诚实部分）

- **与索尼原版互斥**：priority 抢到之后，原版的关机自动传输不会再触发。这是机制决定的。
- **DIADEM 是否另有强制超时**，Java 层看不到。本实现里"等我们"的时间上限由我们自己的
  收尾链决定（无线电沉降 ≤15s，老代码就有的上限），不依赖系统兜底。
- **没能验证"系统是否真会解析到我们"**：阀门能不能被 `queryIntentActivities` 选中，
  取决于本包在相机 App 管理器里的登记方式（与 SonyFTP 一样装成 DLApp）。
  代码侧的兜底是 `ExitCompletedReceiver` —— 万一没接管到、相机不等我们就断电，
  切电前那班岗照样会把关键清理做一遍。

版本 versionCode → **23**；桌面回归 21+164+57+361 全绿；
编译产物已核对：`PowerOffGateActivity` 的 filter/priority=10、`MainActivity` launchMode=2(singleTask)、
dex 里 `param_off_factor` / `poweroff_auto` / `关机自动启动` / `正在关机` 均在。

## 二十一、关机接管"没生效"的排查（vc24 = 临时诊断版）

### 已经查清的部分（不用再猜）

1. **系统侧的机制与文档一致**，我把 smali 逐行读了：
   `DAConnectionManagerService.smali:1433-1456` —— 同一条 action + category，
   `queryIntentActivities(intent, /*flags=*/0)`，然后 `get(0)`；
   之后再无任何准入校验（没有签名/系统应用/注册表检查），直接
   `ACTION_MAIN + setClassName + putExtra("param_off_factor")`。
   把我们筛掉的只可能是**解析与排序**这一步。
2. **全机只有索尼「同步到智能手机」是另一个认领者**：把 dump 里 21 个 APK 逐个
   `aapt dump xmltree` 过了一遍，只有它声明了这个 filter，而且是同一个
   action/category、**没有 priority**（=0）。我们的 10 应当压过它。
   （顺带纠正一条：直接对 APK 做 `grep` 搜不到这个 action —— APK 里的 manifest 是
   压缩的，必须 `aapt dump`。）
3. **我们的包本身没问题**：编译产物里 `priority=10`、`exported=true`、
   `MainActivity` `launchMode=2`(singleTask) 都在；dex 里类与字符串都在。

### 推不出来、只能上机取的部分

两个现象可以归到**同一个根因**：这次关机**没被我们接管**。
- 若我们没被解析到（或排在后面），服务直接落到"没人认领"分支 `setState(4)` →
  黑屏 launcher → 立刻断电 —— 正是①的现象（我们的 `onPause` 即使跑了，
  关闭浮层也被盖在黑屏 launcher 下面）。
- ② 同理：阀门没被拉起，软件自然不会启动。

剩下的疑问只有运行时事实：**那条查询在本机到底命中了谁？阀门有没有被拉起过？
`setComponentEnabledSetting` 成没成功？开关是不是真的开着的？**
相机上没有 adb（系统服务那行 `Slog.d("DAConnectionManagerService", "className = ...")`
看不到），所以做了一版**临时自诊断**，把事实印在相机屏幕上：

- 关于页下方新增一段 26px 灰字（`about_diag`），内容是：
  `开关=` / `阀门=`(getComponentEnabledSetting 回读 0默认1启用2禁用3用户禁用) /
  `装设=`(setComponentEnabledSetting 成没成功) /
  **`查询 命中N 首位:本包(p10)`** ← 用**系统服务那条一模一样的查询**在本机跑一遍 /
  `接管=`(阀门把 extra 递过来的时刻) / `阀门被拉=`(阀门 onCreate 被调用的时刻+off-factor) /
  `暂停=`(最近一次 onPause 的时刻与当时 armed 状态)
- 全部同步 `commit` 落 prefs（`dbg_*` 四个键）：这些事件都发生在关机过程里，
  必须立刻落盘，否则下次开机读到的是空的。

**这段诊断与 `PowerOffGateActivity` 里那次 `dbg_gate_hit` 记录都是临时的，定位完整段删。**
判读方式（下一轮照这个读）：

| 关于页显示 | 结论 | 下一步 |
|---|---|---|
| `查询 命中0` | 我们的 filter **根本没被解析到**（PMCA 包的 manifest filter 在这台机器上可能不参与解析） | 这条路走不通，要换机制或诚实告知 |
| `查询 命中2 首位:com.sony...(p0)` | 被解析到了但**排序输了** | 提高 priority / 查 preferredOrder |
| `查询 命中N 首位:本包(p10)` 且 `阀门被拉=—` | 我们会赢，但阀门**没被拉起** | 查包的 DLApp 登记 / 组件 enable 状态 |

## 二十二、关不掉的那次竞标：固件把第三方 priority 强制清零（根因定案）

用户发来 vc25 诊断屏的照片，一行就把问题钉死了：

```
开关 开
阀门 1  0默认/1启用/2禁用      ← 组件是启用的（setComponentEnabledSetting 成功）
装设 成功
命中 2                        ← 我们**被解析到了**（不是"解析不到"）
首位 synctosmar tp p=0         ← 索尼「同步到智能手机」排第一
次位 本包 p=0                  ← 我们在第二，而且 priority 读出来是 **0**，不是 10
接管 —
阀门被拉 —
暂停 09-13 09:44:54 armed=true
```

`priority` 声明的是 10，编译产物里也核对过是 10（`aapt dump xmltree` 里
`android:priority=(type 0x10)0xa`），**但安装到相机上之后被改成了 0**。

### 去固件里翻到了那处补丁（不是猜测，是读出来的）

`PackageManagerService$ActivityIntentResolver.smali` 的 `addActivity(Activity a, String type)`
（`.line 4806` 起）里有一段**索尼自己加的**逻辑，逐字还原：

```java
boolean systemApp = PackageManagerService.isSystemApp(a.info.applicationInfo);   // v3
for (int j = 0; j < NI; j++) {
    ActivityIntentInfo intent = a.intents.get(j);
    if (!systemApp                      // ← 只针对**非系统应用**
        && intent.getPriority() > 0      // ← 只针对 priority > 0
        && "activity".equals(type)) {    // ← 只针对 activity 过滤器（service 不动）
        intent.setPriority(0);           // 强制归零
        Log.w("PackageManager", "Package " + 包名 + " has activity " + 类名
                + " with priority > 0, forcing to 0");
    }
    ...
}
```

证据链：`grep priority` 在整个 `ActivityIntentResolver.smali` 里只有**一处**命中，
就是那句日志串 `" with priority > 0, forcing to 0"`；它前面紧挨着
`invoke-static {v4}, PackageManagerService;->access$1000(ApplicationInfo)Z`（注释写明是
`isSystemApp`）、`invoke-virtual-quick {v1}, vtable@35`（`IntentFilter.getPriority`）、
`execute-inline {"activity", p2}`、最后 `invoke-virtual-quick {v1, 0}, vtable@51`
（`IntentFilter.setPriority(0)`）。比较器 `PackageManagerService$3.smali` 读的
`ResolveInfo` field@0x28 就是 priority（先比它、大者排前），所以清零直接等于"第三方
永远排不过系统应用"。

**结论：参考文档 §1.3 那句"任何第三方 App 只要写 `android:priority="1"` 就能抢到这次
关机接管权"在这台固件上不成立。** 索尼把这条路从 PackageManager 层焊死了 —— 这多半
就是**因为**存在这类抢注手法才加的补丁。文档作者漏了这一段（他们在 §1.3 只看了排序
规则，没看 `addActivity` 的扫描期改写）。

### 于是只有两条路

| 路 | 做法 | 代价 |
|---|---|---|
| **A. 拿掉竞争者** | 在相机的 PMCA 应用管理器里**卸载「同步到智能手机」** | 失去索尼官方的关机自动传输（文档 §4.3.1 已注明两者互斥）。**这条路现在就能验，不用改代码**：我们都是 PMCA 装进同一个目录的（dump 里 `bi2qfa.sony.ftp-2.apk` 与 `com.sony.imaging.app.synctosmartphone-1.apk` 并排），它可被卸载 |
| **B. 变成系统应用** | 把 APK 装进真正的系统目录（扫描时带 `FLAG_SYSTEM`） | 要动相机的系统分区（刷写/挂载 rw），风险与后续升级成本都高；但能保留官方 App 共存（那时我们的 priority=10 才真的生效） |

`setComponentEnabledSetting` 只能改自己包的组件（改别人的要
`CHANGE_COMPONENT_ENABLED_STATE`，signature 级，拿不到），所以"禁用索尼那个过滤器"
这条也走不通 —— 只能卸载它。

### vc26 补了一条诊断把这件事彻底钉死

`runClaimQuery()` 改成带 `GET_RESOLVED_FILTER` 查询，因此能同时打印：

- `prio/pref/def/m` —— `ResolveInfo` 的**四个排序键**（priority / preferredOrder /
  isDefault / match），也就是比较器实际看的东西；
- `fprio 本包0/它0` —— **filter 自己真实的 priority**（这一条区分"被固件改掉了"
  还是"根本没填进 ResolveInfo"：前者是 0，后者 filter 里会留着 10）；
- `本包sys 0/1` —— 我们有没有 `FLAG_SYSTEM`（决定这条路能不能走通的开关）。

## 二十三、隐藏调试日志屏（vc28）

用户要求：**关于页连续按十下确定键进入日志界面**，详细记录软件的所有动作（含网络行为），
页面要能滚动。追加约束：**日志绝不能落盘**（不碰任何文件），只在屏幕上显示。

### AppLog：纯内存环形缓冲，零文件 IO

新增 `AppLog`（纯 Java，零 `android.*` 依赖，所以能进桌面那道空 classpath 的门）：

- **不碰任何文件** —— 没有 `setSink`/`flush`/`loadTail`，源码里 `java.io`/`File` 出现 0 次
  （包内复核：`debug-log` 等字符串都不在 dex 里；dex 里那个 `OutputStreamWriter` 是
  `PairingStore` 写配对表的，与日志无关）。进程结束日志即消失 —— 它的用途就是
  **"当场做、当场看"**，也彻底避开了"往存储卡写陌生文件触发数据修复"那条老坑。
- 内存里留 **800 行**（环形，满了丢最老的）；写一行 = 拼字符串 + 存数组，无 IO，
  开销可忽略；所有方法 `synchronized`（PTP/IP 连接线程、预取线程、UI 线程都会写）。
- 行格式 `MM-dd HH:mm:ss.SSS 级别/标签 内容`，级别 `I/W/E`。

### 屏幕

- 关于页**连续按十下确定键**触发 —— "连续"的判据是两次间隔不超过 **2 秒**（超了从头数），
  进/出关于页也会清零，所以正常使用不会误触。
- 日志屏结构与其它屏一致：公共顶栏 + 吃满剩余高度的正文 + 52px 底栏（MENU/返回图标）。
  正文是 **ScrollView + 单个 TextView**（26px 多行样式 `FsH26`），**可以滚动**；
  进屏自动滚到最底（最新一条），**确定键 = 手动刷新**（不自动刷新：相机上定时重排
  几百行的开销白吃 CPU），MENU = 回关于页。
- 一屏最多铺 **300 行**（`LOG_SHOW_LINES`）：内存里存 800，屏幕上铺尾部 300 已够看一个
  回合 —— TextView 的排版开销与行数成正比，铺满 800 会明显变慢。

### 打了哪些点（"所有动作"的覆盖范围）

| 域 | 标签 | 记什么 |
|---|---|---|
| 生命周期 | `Life` | onCreate（版本/SDK/上次连接方式）、onResume（当前屏与阶段）、onPause（主动退出还是拨杆竞速收尾）、onDestroy |
| 按键 | `Key` | 每个 keyCode/scanCode **名字化**（UP/DOWN/LEFT/RIGHT/ENTER/MENU/DELETE(垃圾桶)/SK1/SK2/PLAY）＋当前屏 |
| 界面 | `UI` | 每次切屏（`旧屏 → 新屏`，屏名中文化）、主界面按钮、连接设置/已配对设备选中项、主屏状态文本变化、隐藏入口触发 |
| 无线电 | `Radio` | 每条关键广播（Wi-Fi 状态 / Direct 状态 / 组创建 / STA 连断）含关键 extra；请求打开 Wi-Fi 总开关；热点就绪（SSID/IP）；接入点就绪（SSID/IP）；启动失败原因 |
| 网络 | `Net` | 服务端启动（协议/文件/UDP 端口）、协议与文件端口接入（来源 IP + conn#）、Init Cmd Req（手机名/设备码/协议版本）、拒绝接入（原因）、**每条命令**（操作码 + 中文名，PING 心跳除外）、DATA_OPEN 与令牌失效、开始传输（路径/kind/offset/len）、断开（conn#/哪一侧）、服务端停止（拆几条连接） |
| 配对 | `Pair` | 进入/离开配对页、配对成功（手机名）、配对码错误进度、解除配对（设备码） |
| 存储/文件 | `File` `Thumb` `Ftp` | 列目录（路径 → 项数）、预取开始/停止、FTP LIST/RETR |
| 电源 | `Power` | 电量（**只在百分比变化时记**，否则每秒刷屏） |
| 退出 | `Exit` `Mode` | 有序退出开始（方式）、收尾开始、切换连接方式（旧 → 新，是否设为默认） |

刻意**不记**的：`PING` 心跳（3 秒一次，记了会淹掉日志）、每秒的 ticker（只记"变了"）。

### 回归测试

`desktop-test/AppLogTest.java`（+12 条断言，已接入 `run-tests.sh` 的 `[4b/5]` 步）：
容量封顶在 800 且**丢最老的**、绕圈之后行序仍严格递增（无错位）、`dump(n)` 只给尾部、
`dump(0)` 给全部、级别带上、异常信息带上。`AppLog` 也加进了内核编译列表（零 Android 依赖）。

### 预览工具补上折行（用户："屏幕边缘要换行 要不都挡上了"）

用户看到的第一版预览图里长行直接被画布裁掉了。**那是预览工具的失真，不是工程的问题** ——
真机上 TextView 宽度受 ScrollView 约束（`match_parent`，左右 padding 各 8px → 624px），
超宽的行会自动折行，没有空格的超长路径也会被 emergency-break 拆开。

但**预览失真本身就是 bug**：这个工具的职责就是"先把每屏合成出来看一眼，认可之后才动工程"
（资源包错误记录 #29 的教训）。所以给 `mk_ui_preview.py` 加了 `wrap_lines()`：
按**渲染后宽度**逐个字累加拆行，`screen_log` 用它逐行绘制，并同样遵守"画到内容区底就停"。
这样预览图和真机才是同一件事。

## 二十五、配对页的按键分工纠正（MENU=返回 / 垃圾桶=菜单）

| 按键 | 改前 | 改后 |

| MENU | 打开选项菜单 | **返回**（落点 = 进配对页之前那一屏） |

  浮层（切换浮层 / 设为默认询问框）底下压着的本来就是那个面板，用户按返回时看到的

## 二十六、转盘拨轮全局支持 + 方向键语义分开 + 弹窗"其它键即退出"（2.0 第二轮）

用户三条要求：

1. **增加软件内全局对转盘拨轮的支持**；
2. **不要模糊上下键与左右键的语义** —— 上下排列的按钮只认上下键，左右排列的只认左右键；
3. **有"取消"的弹窗**（功能设置弹窗除外）里，除上下键外的**任何键都直接退出弹窗**。

### 转盘的扫描码：去固件里读，不猜

`ISV_DIAL_*` 的值此前工程里没有。这次直接从相机固件里那份库读出来了：

- `framework/com.sony.scalar.sysutil.ScalarInput.odex`（固件 v2.01，19,904 字节，
  odex 头 0x28 字节之后就是 dex）；
- 用它自己写的 60 行 Python 解 dex：`class_data_item` 的静态字段 + `static_values`
  编码数组 —— **184 个字段一个不差**全拿到了。老那 10 个常量与 OpenMemories 那版逐项一致，
  所以桩的可信度这次是"从设备里读出来的"，不是抄社区文档。
- 工具链也顺手补齐了：`6300fw/tools/baksmali` 那套 jar 里 jcommander 版本不对
  （1.78 删了 `getMainParameter`、1.12 又太老），baksmali 起来就报 NoSuchMethodError；
  真要反汇编时换一份 1.64 上下的 jcommander，或者像这次一样直接解 dex。

转盘那一族的值：`ISV_DIAL_KURU_CLOCKWISE/COUNTERCW = 522/523`、
`ISV_DIAL_1_* = 525/526`（STATUS 524）、`ISV_DIAL_2_* = 528/529`（STATUS 527）、
`ISV_DIAL_3_* = 634/635`（STATUS 633）。`*_STATUS` 是"这个转盘的存在/状态"广播，
**不是转动事件**，所以代码里显式收下不动（更不能让它落进"其它键"那条规矩里去关弹窗）。

同一份 dex 里还有个功能枚举 `FUNC_CONTROL_WHEEL_NEXT/PREVIOUS`、
`FUNC_THIRD_DIAL_NEXT/PREVIOUS`、`FUNC_LENSRING_NEXT` —— 索尼自己也是把这几个转盘
统一当"上一个/下一个"用的。另外 KeyStatus 只是个状态壳（`status` + `getKeyStatus` +
`getKeyLogicCode`），**没有"转了多少格"这种 API**，所以转动必然是以**按键事件**
（scanCode = 上面那些 DIAL_*）送进来的，不存在"轮询累计角度"的另一条路 ——
这一点决定了实现方式，否则就会去写一个永远读不到东西的轮询。

### 实现：移动逻辑只留一份 `step()`

按键与拨轮都往同一个方法里汇，语义不会各自长歪：

| 输入 | 传给 step 的方向 |
|---|---|
| 上下键 | `STEP_UP` / `STEP_DOWN` |
| 左右键 | `STEP_LEFT` / `STEP_RIGHT` |
| 拨轮顺时针 | 竖排屏 = `STEP_DOWN`；主界面（横排）= `STEP_RIGHT` |
| 拨轮逆时针 | 竖排屏 = `STEP_UP`；主界面 = `STEP_LEFT` |

`step(dir)` 按**当前屏怎么排的**决定走不走得通：

- `SCR_MAIN`（两颗按钮**横排**）：只认左右 → **上下键在这里什么都不做**（这就是用户说的
  "不要把语义搞混"：以前上下键也能在左右两颗按钮间跳，确实是模糊的）；
- `SCR_MENU` / `SCR_MODE` / `SCR_PAIRED`（竖排列表）：只认上下 → 左右键不动焦点；
- `DLG_CONFIRM` / `DLG_DEFAULT`（两颗按钮**竖排**，原厂坐标 274/340 就摆在那儿）：只认上下；
  单按钮通知态没有第二颗可去，上下键也不动（沿用原先那条 `noticeMode` 护栏）；
- `SCR_LOG`：没有可聚焦的行，上下（与拨轮）改成**翻正文** —— 一屏铺 300 行，
  以前在机身**根本滚不动**（ScrollView 没被 focus，方向键到不了它），这是顺带补上的洞；
- `SCR_PAIRING` / `SCR_ABOUT`：没有可动的东西，按键与拨轮到此为止。

**拨轮在弹窗里算"上下"**（即移动，而不是退出）：用户要的是"全局支持转盘拨轮"，
在索尼机身上转盘本来就是"在选项之间走一格"的那个控件。这一条与第 3 条要求
（除上下键外任何键退出）在字面上有交叉，我按"拨轮 = 上下"处理；要改成"拨轮也算其它键、
在弹窗里直接退出"，改 `onDial()` 一个分支即可。

### 弹窗"其它键即退出"（`exitDialogByStrayKey()`）

判据是 `screen == DLG_CONFIRM && !noticeMode` —— 也就是**只有带"取消"的确认弹窗**
（退出软件 / 解除配对 / 进入配对模式）吃这条规矩：

- 左右键 → 退出（竖排按钮对里左右键本来就不是"移动"）；
- 垃圾桶键、Fn/DISP/S1/自定义键等**一切落到 `default` 的键** → 退出；
- 退出 = 走"取消"那条路（回弹窗下面那一屏），**不是**执行确定；
- **确定键仍然是执行焦点上的那一个按钮** —— 否则弹窗就没法确认了。用户原话是
  "除上下键外任何键都退出"，字面上把确定键也算进去，但那样弹窗就废了，所以这里是
  按"能不能用"取的舍；
- 单按钮通知**不适用**：它没有"取消"，"任何键都退出"会等于"任何键都执行确定" ——
  尤其"请先与一台手机配对"那条，随便按一下键就进配对页，恰好废掉用户要的那道确认；
- 功能设置询问框 `DLG_DEFAULT`（设为默认 / 仅本次）**按用户要求排除**：它不吞键也不退。
  这一条也说得通 —— 它的第二颗按钮是"仅本次"，让一个误触的键替你选"仅本次"是**替用户做决定**，
  不是"退出"。

### 日志那边顺手对齐

`onKeyDown` 的日志行改成 `scan=<值>(<名字>) keyCode=<值> screen=<屏>`：相机上这些索尼
私有键的 `keyCode` **恒为 0**，认键只能靠 scanCode，老写法把两者写混了。
`keyName()` 补全了转盘（"拨轮KURU顺时针"这类）与 Fn/DISP/AEL/C1-C3/模式转盘/曝光补偿转盘/
光圈转盘/S1/S2 的名字 —— 用户要验"机身这个转盘到底报的是哪一个"，在日志屏转一下就能读出来。

### 验收（真机）

1. 主界面：左右键在"Wi-Fi 设置/服务状态"两颗按钮间切换；**上下键不再动焦点**；
2. 拨轮：主界面转动 = 左右切换；进选项菜单/已配对设备/连接设置后转动 = 上下走行；
   在"退出软件？"这类弹窗里转动 = 在确定/取消之间移动；
3. 弹窗：按左右键 / 垃圾桶键 / Fn / DISP 等**任何非上下键** → 弹窗直接消失（等于取消）；
   按确定 → 执行焦点上的按钮；
4. 日志屏：上下键或拨轮能翻正文（原先滚不动）；
5. 若某个转盘在界面上没反应：进日志屏转一下，把 `scan=` 那行的名字/数字发我 ——
   机身若有第 5 个转盘（这台的固件里只有 KURU 与 1/2/3 四个），照着加一个 case 即可。

## 二十七、主屏辉光（重画）+ 退出改全屏黑底 + 电量分档照抄原厂（2.0 第三轮）

用户三条：① 把「同步到智能手机」主屏下方那束辉光抄过来，只在主屏显示；
② 退出界面改成"全屏黑底那个全屏提示窗"；③ 电池图标对电量的映射不准确，看原版怎么映射的。
期间用户补了一句：原版辉光的渐变断层很严重，**修复/优化渐变效果**。

### 1. 辉光：原厂槽位 + **重画一条平滑渐变**（不直拷）

原厂那张是 `p_16_dd_parts_sync_background.png`（640×298 @屏(0,130)，在
`main_layout_panel_default.xml` 里是**最后一个子节点** = 画在最上层；它也是原厂"屏幕下方
渐亮"的观感来源）。位置落法：正文区是 66..428，所以"贴正文底往上铺满"正好等于 130..428，
工程里就是 main_body 里一个 `layout_gravity="bottom"` 的 298 高 ImageView。

**但不直拷**：那张图只有 **5 级 alpha（0/17/34/51）+ 网点抖动**，真机上就是用户说的断层。
做法（`tools/ui/mk_ui_assets.py: glow_main()`）：

- 先量原图的**逐行有效 alpha**（抖动只是用网点近似小数 alpha，逐行平均正好还原出作者
  本来想要的那条曲线）→ 得到 0 → 45.16 的包络；
- 再把它做 15 行移动平均 + 单调化，逐行取整 → 一条平滑单调的 8 位渐变
  （相邻行 alpha 差最多 1，298 行里 45 个台阶，肉眼无条带）；
- 颜色取 #DDDDDD（原图可见像素的众数，与标题/图标同一套灰）；文件 1.5 KB（原图 9.4 KB）。

有一点在真机上要留意：帧缓冲若是 16 位（RGB565），这么暗的一段渐变在**合成之后**仍可能
被量化回几档（红蓝 5 位 = 每档 8）。素材这边已经做到"源头无台阶"，再往上就只剩
"要不要加细网点抖动"这个取舍了 —— 用户明确不喜欢原版那种网点，所以先不加。

### 2. 退出/切换界面：全屏黑底

`poweroff_layout_panel.xml` / `boot_layout_panel.xml` 都是 `match_parent` + `#ff000000`
且**什么内容都没有**；退出时用的 `exit_screen.xml` 是整屏黑 + 一条 640×60 的 FooterGuide

反应，写着"MENU 返回"是骗人的（原厂那屏的 FooterGuide 就是空文案）。
`footer_key_dlg_exiting` 随之从布局与 `applyIconFont` 里一起删掉，不留半截引用。

### 3. 电量分档：照抄原厂 `BatteryIcon.checkBatteryLevel()`

原版就在「同步到智能手机」的 APK 里：`com.sony.imaging.app.base.common.widget.BatteryIcon`，
smali `checkBatteryLevel(I)I` 反出来是：

```
value < 1              → level 0     （0 与"读不到"都给空图）
value <= list[2]       → level 1     （默认 list = {80, 50, 20} →  1..20）
value <= list[1]       → level 2     （21..50）
value <= list[0]       → level 3     （51..80）
否则                    → level 4     （81..100）
```

阈值来自系统属性 **`ui.battery.threshold.list`**（`ScalarProperties.getIntArray`），
读不到才用代码里写死的 {80, 50, 20}。**我们之前用的 10/35/60/85 是自己编的**，
这就是"映射不准确"的根因。现在：

- 新增 `batteryThresholds()`：运行时读那个属性（读不到就用原厂兜底并把这件事写进日志）；
- `checkBatteryLevel(value)` 逐行照抄原厂判断（含"读不到 → 0 档"）；
- 档位图与原厂一致：**level 0 = error 图**（ScalarA 那套 `icon_battery` level-list 里
  level 0 指的就是 `s_16_dd_parts_169_scalar_prin_buttery_error`，也就是我们已有的
  `bat_err`），1..4 = `bat_1..bat_4` —— 所以**素材一张都不用换**，只是档位线对了；
- 日志里连档位一起记（`电量 87% → 第 4 档`），真机上一眼能对。

### 4. 用户复核后的两处返工（同一轮内）

**（a）辉光"块状横条" → 加有序抖动。** 第一版只做了平滑（相邻行 alpha 差≤1），
真机上却是几道"块状横条"—— 说明这块屏的**合成输出被量化**了（按 16 位 565 算：
灰洗色 #DDDDDD 在 alpha 0..45 时合成出来只有 0..39，红/蓝每档 8 → 只剩 5 档）。
平滑的源头救不了后端的量化，于是给 `glow_main()` 加了 **4×4 Bayer 有序抖动**，
幅度取**一档**（颜色域 8 → alpha 域 ≈ 9.2）：每一档之间多出 16 个子阶，观感连续、
图案细（1px 网点，屏上因横向 ×2 拉伸成 2px 宽的对子）。素材从 1.5 KB 变成 6.9 KB。

**（b）退出界面 → 恢复"最开始那个带四边外框的全屏"版式。** 用户原话：
"退出界面我要的是那个带四边边框的全屏退出界面，下面没有提示栏的那个"
以及"为什么要自己画呢，你之前最开始是用过这个布局的"。

翻历史核对：**换装第一版（`29b569d`）的主界面**用的就是"600×468 @(20,6) 的 1px 外框"
（`panel_frame.xml` + `@color/frame_line` = #555555），后来在 `4b0f74f` 里按原厂真值
删掉了（原厂主界面靠顶栏/底栏内侧的 #333333 细线分区，没有外圈框）。`frame_line`
这个色值当时没跟着删，一直留在 colors.xml 里。

所以返工的做法就是**把它取回来、只给退出那一屏用**：
- 恢复 `res/drawable/panel_frame.xml`（一字不改地还原，注释里写明它是"换装第一版"
  那个外框、现在归退出屏）；
- `dlg_exiting` = 整屏纯黑 + 一个 600×468 @(20,6) 的装饰 View（background=panel_frame）

### 7. 退出屏正文位置也按照片实测挪位
