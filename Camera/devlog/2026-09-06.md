## 追加（第八轮：静态分析定案 → 单进程纯 Java 重构，v1.3）

用户判定日志路线到头（崩溃快过 Java 崩溃处理器，CRASH 段写不出），转入静态
分析 ma1co 四包（Tweak/Platform/Framework/PMCADemo）+ 索尼固件资料。

### 静态分析结论

1. **OpenMemories-Framework 是纯 Java**：DeviceInfo.CameraDeviceInfo 用
   ScalarProperties（索尼自带 Java API）读型号/序列号/固件：
   getString("model.name") / getString("model.serial.code") /
   getFirmwareVersion()。键值真值取自其 jasmin stub。
2. **PMCADemo 全程单进程**：manifest 只有 receiver+activity，无 service、
   无 android:process；序列号读取即上述纯 Java 路。
3. **Tweak 原生库**：GCC 4.9 / armeabi(ARMv5) / APP_PLATFORM android-9 构
   建；其 exec 只拉原生二进制（telnetd/adbd），从不派生第二个 dalvik 进程。
4. **我方 .so 体检**：DT_HASH 存在（hash-style 无辜），但 v7a + r23c 与平台
   无从验证；真正致命的不是 .so 本身——

### 三路径同因：给应用派生第二个 Android 进程 = 进程组被杀

- 启动预热：warmUp → probe → startService(:info)；
- 关于页：AboutLoader → info() → probe → startService(:info)；
- 手机扫描后崩溃：ConnectHandler INFO → info() → 同上；
- 更早的 Runtime.exec dalvikvm 子进程同样是"派生 Android 进程"。
- SIGKILL 特征吻合：Java 崩溃处理器来不及写任何 CRASH 段。
- Tweak exec telnetd（原生二进制）无事 → 平台禁的是"再多一个 dalvik 进程"。

有时连不上 Wi-Fi，界面显示 Wi-Fi 实际仍是热点模式（热点没关）；③"WiFi
设置"行去掉"系统界面"描述。

根因与修复：
1. **模式切换不撤旧模式回调**：beginModeSwitch/wipeModeAndRechoose 缺
   removeRadioCallbacks()——热点的"5s 延时使能""30s 启动看门狗"活着进入
   Wi-Fi 模式；看门狗在 Wi-Fi 轮询期间误触发 goFatal → 强关无线电 → 连不上。
   （退出/onDestroy 路径原本就有撤回调，唯独切换/清除漏了。）
2. **Direct 关闭单发即走**：shutdownServicesAndRadio 热点分支只发一次
   setDirectEnabled(false) 再等 10s；驱动沉降慢时带着残留热点就切进 Wi-Fi。
   改为未确认沉降前每秒补发（强制退出路径同款），截止 15s。
3. **startStationFlow 双保险**：入场先 removeRadioCallbacks + 若
   isDirectEnabled 则补发关闭并确认沉降（≤8s），再开 Wi-Fi。
4. **Wi-Fi 名称偶发缺失**：固件在关联刚完成时回 "<unknown ssid>"——
   stationSsid() 把占位串视为 null；拿到 IP 后若名称未就绪最多再等 3s；
   主页状态栏 Wi-Fi 名称实时重读（存储值作兜底）。
5. modeItems "WiFi 设置"值清空（原"系统界面"）。

## 追加（第十二轮：热点残留真根因——缺 removeGroup，v1.7）

用户复测：热点仍未关闭。深挖 RadioWrapperJb 发现两个叠加问题：

1. **只关开关、没拆组**：此前收尾只调 setDirectEnabled(false)——它关的是
   "Direct 功能开关"，本固件实测可以留下仍在广播的 GO 组壳。标准
   WifiP2pManager.removeGroup() 才是拆组的命令。RadioWrapper 接口新增
   removeGroup()：Jb 实现走标准 removeGroup（等应答≤8s），Gb 路线
   DirectManager 同步关 Direct 即等效。
2. **确认查询会撒谎**：radiosConfirmedDown 用的 isDirectEnabled() 走
   ExtManager 回调查询——本固件"应答回调迟迟不派发"（wrapper 注释在案），
   超时只能返回 false，即组还活着也报"已关"，补发循环第一次就提前收工。
   改用标准 requestGroupInfo（getLiveGroup()==null）做组壳存活的真值判定。

修复落点：
- shutdownServicesAndRadio 热点分支：removeGroup + issueDirectOff + 关 WiFi
  三连，未确认（WiFi 关 && 组消失）前每秒补发，截止 15s；
- startStationFlow 双保险②：入场改查 getLiveGroup()，组壳存活则
  removeGroup+issueDirectOff 循环确认消失（≤8s）再开 Wi-Fi；
- runForcedExitCritical 后台补发环加 removeGroup；
- RadioWrapperJb 新增 removeGroup()，RadioWrapperGb 等效实现。

## 追加（第十三轮：热点"复活"真凶——状态机接收器未注销，v1.8）

用户复测并点破关键现象：切 Wi-Fi 模式走完关闭流程后报"无法启用Direct模式"
——可 Wi-Fi 模式根本不需要 Direct。这指向热点启动状态机还活着。

**真凶实锤**：热点的无线电事件接收器（receiver/iFilter）只在
initAndStartWifiCycle 注册，从不在离开热点模式时注销。切到 Wi-Fi 模式后：
startStationFlow 一开 Wi-Fi 总开关 → 系统发 WIFI_STATE_ENABLED 广播 →
僵尸状态机被唤醒 → handleWifiStateChanged(ENABLED) → issueDirectEnable()
→ Direct 起不来报"无法启用Direct模式"并 goFatal 回滚（把 Wi-Fi 也关了）；
Direct 若起来了则 handleDirectStateChanged(ENABLED) → startGroupOwner()
**把刚拆掉的热点重建**。这解释了此前 removeGroup 之后"热点仍然没关"。

修复（两层）：
1. shutdownServicesAndRadio 热点分支收尾时 unregisterReceiver(receiver)
   （与注册对称；退出路径已注销的场合吞掉 IllegalArgumentException）；
2. handleEvent 顶部加模式守卫：`shuttingDown || 非热点模式` 一律忽略——
   即使接收器仍在（注册两次等边缘情况），Wi-Fi 模式下任何广播都驱动不了
   热点状态机。

语义与用户预期一致：切 Wi-Fi 模式 = 完整走一遍热点退出（含状态机注销），
然后只开 Wi-Fi 开关让系统自动连。
