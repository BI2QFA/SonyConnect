# 2026-09-13 相机端：配对待机态流程 + 菜单精简 + 按钮居中

用户先给了三件事，装机试跑后打回一次并补了语义定义。两次原话：

> 首次进入时那个连接方式和配对模式的按钮错位了 不在横轴中央 另外流程改一下 当没有选择连接方式
> 没有本地已配对设备时询问连接方式后不等待服务启动完成 直接进入一个专门的配对模式屏幕
> 此界面后续在设置中可以再次进入 选择完连接方式后应在后面自动启动服务 然后正常进入配对待机流程
> 为了照顾到有的设备并没有设置自动连接的wifi的问题 配对模式时的menu菜单精简到只有连接模式选择
> （选择完后应重新进入配对界面）wifi设置，关于，退出软件 一些逻辑问题你自己注意一下

> 你的软件在首次启动选择完连接方式后并没有自动进入配对界面 我这里首次启动的语义是 当检测到本地
> 没有配对设备时 这个语义下启动的配对界面应精简菜单 正常状态下用户手动在设置进入的配对界面
> 不应精简菜单 菜单应与正常状态下无异 重新修改

## 一、单按钮通知弹窗偏心（一句就够）

`showNotice()` 借的是**双按钮**确认面板，原来把"取消"设成 `View.INVISIBLE`：

```java
btnConfirmCancel.setVisibility(View.INVISIBLE);   // ← INVISIBLE 只是不画，仍然占着布局
```

按钮行是"确定 240px + 24px 间距 + 取消 240px"**整体居中**的（`layout_centerHorizontal`），
藏掉取消之后确定按钮落在**左半边** —— 正是用户看到的"不在横轴中央"。

改法：`View.GONE`（彻底不参与布局，剩下那一个按钮自然居中），收尾时恢复 `VISIBLE`。

## 二、首启没进配对页：真因是**配对表建得太晚**

第一版实现写的是：

```java
final boolean toPairing = modeFromPairing
        || (!modeFromMenu && pairingStore != null && pairingStore.size() == 0);  // ← 恒假
```

`pairingStore` 原来是在 **`startServices()` 里懒建**的（`if (pairingStore == null) new PairingStore(...)`），
而首启"选完连接方式"那一刻服务还在后台起 —— 那时它还是 `null`，条件永远为假，
界面就停在主界面不动。用户实测到的正是这个。

改法：`PairingStore` 挪到 `onCreate` 就建。它是**纯文件存储**，既不依赖无线电也不依赖
PTP/IP，而"本机有没有已配对设备"这件事**必须在服务起来之前**就能回答（配对待机态的全部
判断都建立在它上面：进不进配对页、配对页的窗口能不能开）。`startServices()` 里的懒建
保留成空保护。

## 三、"精简"的判据是**进入原因**，不是"当前在配对页"

用户给语义定义之后，判据从"页面"改成"来路"，落成一个字段：

```java
/** 配对待机态：因为"本机没有已配对设备"而自动进入配对页（用户定的语义）。 */
private boolean pairingStandby = false;
```

| 进入方式 | pairingStandby | 菜单 | 菜单的"上一级" |
|---|---|---|---|
| 检测到**没有已配对设备**时自动进（首启选完方式 / 启动时无配对记录） | true | 精简 4 项 | 配对页（它才是这一态的家） |
| **正常状态下**用户从菜单手动进（已有配对设备） | false | **与主界面完全一致**（连接设置 / 配对模式 / 关于 / 清除软件数据 / 退出应用程序） | 主界面（照常） |

于是第一版里我自作主张加的"返回主界面"那一行**删掉了**：正常态走的是完整菜单，
它的 MENU 本来就回主界面（配对页不再是单向门）；待机态留着那 4 项与用户定版一致。

精简那 4 项（仅待机态）：**连接模式选择 / Wi-Fi 设置 / 关于 / 退出软件**，其中
"连接模式选择"选完**回配对页**（`modeFromPairing`）—— 用户定版，配对页才是这一屏的家。
配对待机态下按 MENU 进的就是这份精简菜单，选完方式回来窗口重开、码也会是新的。

## 四、能不等服务的原因是"窗口与服务是两件事"

配对窗口（6 位码 / 180 秒）在**进配对页**时就开了，服务器随后才到 —— 手机连上来时
服务器才查"窗口开着没、码对不对"，所以顺序无所谓。这就是"选完连接方式不等服务启动完成
直接进配对页"能成立的前提（`enterPairingMode` 只碰 `PairingStore`，不碰服务）。
服务在后台照常起来（`beginModeSwitch` → 后台线程 → `applyMode`），就绪后只刷主界面的
状态文本，**不会抢屏**（`updateMainStatus()` 只改文本，不切页面）。

## 五、顺手堵掉的三个洞（"一些逻辑问题你自己注意一下"）

1. **配对倒计时心跳会死**：`pairingTicker` 原来是 `if (screen != SCR_PAIRING || shuttingDown) return;`
   —— 切换连接方式期间 `shuttingDown` 为 true，而新流程恰好在"切换中"就进了配对页，
   心跳被 return 掉**且不再重排**，配对页的"剩余 N 秒"会永远停在某一下。
   改成"不在配对页才彻底停；在配对页就继续排，只是 shuttingDown 期间跳过刷新"。
2. **菜单焦点越界会崩**：`moveFocus` 用写死的 `menuItems.length`（5）。精简菜单只有 4 行时
   焦点能走到 index 4，`RowAdapter.getView(4)` → `items[4]` 越界闪退。改用适配器当前行数。
3. **服务起不来时界面还停在配对页**：无线电失败（连不上 Wi-Fi / Direct 创建失败）时，
   错误文案与"[确定键] 重试"都在主界面上，用户却盯着配对页的 6 位码，只会以为手机连不上。
   `goFatal()` 里补一条：在配对页就关窗 + 回主界面，让失败可见。
