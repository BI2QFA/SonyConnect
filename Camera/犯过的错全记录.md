# 犯过的错 · 全记录（Mistake Log）

> **给接手的 AI**：这份文档是本项目从开始到现在**所有犯过的错**的完整清单，
> 按类别组织。每条都有：错误做法 → 后果 → 正确做法 → 怎么提前发现。
> 与 `交接文档_HANDOFF.md` 第 9 节的踩坑清单互补——那边是"结论"，这边是"事故现场"。
>
> 之所以整理它：本项目最大的一次返工（demo 两版被评"差太多/仍然不对"）和最近一次
> bug（警告图标错位）都**不是能力问题，而是流程问题**。读完这份，你就不会再犯。

## 一、方向性错误（最贵的一类，返工以天计）

### 1. 解析错了系统：去逆向 Linux 主系统 UI
- **错误做法**：拿到固件后直接开始分析，没分清 A6300 有两套 UI
- **后果**：`nflasha15`（Linux 主系统，`libviewUnified2.so`）的成果全部作废，
  被用户连续纠正两次（"先停，我要的是安卓端"、"6300 有两套菜单"）
- **正确做法**：开工前先确认分区映射并写进常备笔记：
  `nflasha15 = Linux 主系统` / `nflasha16 = 安卓子系统(框架)` /
  `nflasha17 = 可安装的 PlayMemories 应用`
- **预防**：任何"从固件里找"的任务，第一步先输出一张分区↔用途映射表给用户确认

### 2. 靠猜测而不是先读固件
- **错误做法**：demo v1 直接凭印象写 UI（猜字号 8px、猜橙色 #DD9900、
  拿错 MenuData 数据源、没有用原厂素材）
- **后果**：两版 demo 被评"差太多"、"仍然不对"，全部重做
- **正确做法**：**先 dump 再写**。每写一行 UI 代码，对应数字必须能指出
  来自哪个文件的哪一行 dump（布局=`08_layouts_kv.txt`，颜色=`02_colors.md`）
- **预防**：把"这个值哪来的？"变成自查问题；答不出来就是还没到写代码的时候

### 3. 误把 nflasha17 的 App 当成"只有 odex 没有 dex"
- **错误做法**：nflasha16 系统 App 确实是 `classes.dex` 被抽成 odex，
  我把这个认知错误地推广到了 nflasha17 的 21 个 PlayMemories 应用
- **后果**：晚了很多轮才发现每个 App 的 APK 里**都有完整 classes.dex + 布局 +
  MenuData.xml**，错失了早期就能读代码、做数据驱动引擎的机会
- **正确做法**：`zipfile.ZipFile(apk).namelist()` 一分钟就能验证的事，先验证再下结论
- **预防**：对"某类文件不存在"的结论，必须列出实际列举过的证据

### 4. 弹窗"凭记忆近似"而不 dump 布局
- **错误做法**：做 Lite 版弹窗时按当时记忆里的数字摆（按钮 x=220、
  自造标题、进度条 440×10、警告图标位置靠印象）
- **后果**：用户实测"按钮位置、文字大小、边缘灰线很多都是错位的"，整体返工
- **正确做法**：每个弹窗单独 `aapt dump --values xmltree` 逐元素抄坐标
  （单按钮/双按钮/带图标/居中/进度条是 5 个不同的布局文件）
- **预防**：一个屏只要有一个数字是"我记得大概是"，这一屏就没资格编译

## 二、测量与换算错误（都是心算惹的祸）

### 5. ★ 十六进制换算心算翻车（最近一次 bug）
- **错误做法**：警告图标 `marginLeft=0x12200`，我心算 `0x12200>>8 = 74`
- **后果**：真值是 **290**。更糟的是第一版 Lite 本来写对了 (290,20)，
  被"校准"改错成 (74,4) —— **把对的改成了错的**
- **正确做法**：`python -c "print(0x12200>>8)"` → 290
- **预防**：**十六进制换算禁止心算**，一律脚本复核；改"已经验证过的值"之前
  必须重新核对 dump 原文（git diff 式自问：我为什么改动这个数？）

### 6. 把字号名里的 W29 当成比例
- **错误做法**：`PFontSize.H38W29` → 29/38 = 0.7632，写进 row_menu.xml
- **后果**：与真值 0.7001 不符（名字里的 W 不是简单比例）
- **正确做法**：从 framework style bag 提取权威值：**全 UI textScaleX = 0.7001**
  （仅 H52W48 = 0.8846），见 `01_文档/03_styles.md`
- **预防**：命名规则里的数字是"设计意图"不是"渲染参数"，渲染参数以 style bag 为准

### 7. 截图↔逻辑坐标的 Y 标度测错
- **错误做法**：早期把录屏 2670×1200 → 640×480 的 Y 标度算成 2.39
- **后果**：纵向所有对位偏差（后来用分隔线等距性验证出应为 **2.5**）
- **正确做法**：用**多个等间距元素**（如分隔线 y 175/277/328/379/430）做线性回归，
  而不是两点求斜率
- **预防**：坐标映射必须用 ≥3 个点交叉验证，并写成脚本（`m4.py/m5.py`）

### 8. 布局值误写一个数量级
- **错误做法**：`marginLeft=0x1100` 曾被记成 272px
- **后果**：列表宽度结论错误
- **正确做法**：0x1100>>8 = **17px**
- **预防**：同第 5 条；另外所有布局值入库时顺手写上十六进制原文备查

### 9. framework 资源 ID 少写前导零
- **错误做法**：拿 `0x10808dd` 去查表（dump 里是 `0x010808dd`）
- **后果**：查不到，误以为资源不存在
- **正确做法**：framework ID 恒为 8 位；查不到先补零再查

## 三、Android API 使用错误

### 10. `setTextSize(42f)` 是 sp 不是 px
- **后果**：相机密度 ≠ 1，文字被放大约 1.66 倍（SonyMenuEngine 被用户报"字号不对"）
- **正确做法**：`setTextSize(TypedValue.COMPLEX_UNIT_PX, 42)`；
  XML 里写 `android:textSize="42px"`

### 11. 把 `View.setScaleX` 当成 `android:textScaleX`
- **后果**：整个 View 绕中心缩放 → 右对齐引导被拉左、左对齐标题被拉右
  （被用户报"标题和右下角图标错位"）
- **正确做法**：`TextView.setTextScaleX(0.7001f)`（等价 XML 的 textScaleX，只缩文字）

### 12. 9-patch 重建用"整圈黑色 marker"
- **后果**：Android 把边框也当可拉伸内容 → 圆角/1px 边缘线跟着拉伸变形
  （被用户报"边缘灰线错位"）
- **正确做法**（mkassets 技术，实机验证过）：原图整体贴到 (1,1)，
  外圈只在**可拉伸段**画纯黑 marker，四角透明

### 13. 索尼 9-patch 的 #DD7700 marker 直接编译
- **后果**：AAPT2 拒收（`top-left corner pixel must be either opaque white or transparent`；
  后来还发现四角不透明也会被拒）
- **正确做法**：重建 marker 环；永不拷固件原图当 .9.png 用

### 14. 底部引导用图片（guide_menu.png/guide_exit.png）
- **后果**：与真机"MENU 键帽+返回箭头"完全不像（用户一眼指出）
- **正确做法**：FooterGuide 是个 TextView，内容是图标字体字符串
  `"\uE80A\uE803"`（Sony_DI_Icons.ttf），36px/0.7001 右对齐
- **教训**：素材长得像图片 ≠ 是图片；先读实现类（FooterGuide.smali 只有一个 TextView）

### 15. 尝试跨 App 复用索尼自定义 View
- **后果**：类加载器隔离，`ItemAlignedListView` 等无法 inflate
- **正确做法**：自写同名 View 或按真值几何程序化绘制（Demo3 验证可行）

### 16. 第一版引擎用代码画 UI 而不是复用已验证的 XML
- **后果**：同时踩了第 10、11 条（XML 版的 Demo3 早就验证过几何）
- **正确做法**：**能复用已验证产物就复用**；程序化绘制只用于动态部分
  （页码数量、行内容），静态骨架留在 XML

## 四、解析器错误（都在 aapt dump 的消费端）

### 17. `aapt dump xmltree` 的布局文件写成了 `--file`
- **后果**：报 "resource not found"，**且不提示参数用法**，极易误判文件不存在
- **正确做法**：`aapt dump --values xmltree <apk> res/layout/x.xml`（位置参数）

### 18. 资源行正则没考虑包分隔符
- **后果**：`(\S+):(\S+):` 全部匹配失败，第一版三本字典为空
- **正确做法**：行格式是 `resource <id> <pkg>:<type>/<name>: <值>`，
  第一个冒号属于包名

### 19. config 行括号两种写法 / 非 default 配置块
- **后果**：中文与部分颜色取不到（颜色常落在非 default 块）
- **正确做法**：`config (default):` 与 `config zh-rCN:` 都要兼容；取值带回退

### 20. aapt xmltree 缩进树不弹栈
- **后果**：每个选择器只解析出**第一个 item**，且不报错（静默错）
  ——状态表第一版 `menu_list_selector` 5 条只剩 1 条
- **正确做法**：按缩进 pop 栈建树（`ref6.py` 的 parse()）

### 21. style bag 只有数字 Key
- **后果**：无法知道 `Key=0x01010095` 是 textSize，交叉引用全断
- **正确做法**：先用 IDMAP（spec 行）把 Key 还原成属性名

### 22. Res_value 类型码/单位码混淆
- **后果**：FRACTION 用了 DIMENSION 的单位表 → `fromYDelta=1.2px` 这种荒唐值
- **正确做法**：类型码 0x05=DIMENSION（0=px 1=dip…）、0x06=FRACTION
  （**0=相对自身 1=相对父容器**）；packed 解码
  `value = (raw 取 int32 符号 & 0xFFFFFF00) * RADIX[(raw>>4)&3]`

### 23. 动画 XML 跨限定符重名
- **后果**：文档里写出不存在的 `res/anim/task_open_enter.xml`（实际在 anim-land/anim-port）
- **正确做法**：引用资源一律带限定符前缀

### 24. Sony_DI_Icons 的 post 表想当然
- **后果**：以为能拿到图标语义，实际字形名全是 `uniXXXX`
- **正确做法**：从字符串资源里"图标后紧跟的英文单词"反推（43 个），
  再用 PIL 渲染图鉴人工确认

## 五、工程与流程错误

### 25. 生成脚本里 `rmtree` 整个工程目录
- **后果**：`mk_lite1.py` 重跑时把手写的 MainActivity/Manifest/gradle 全清了，
  被迫重写
- **正确做法**：生成脚本与手写文件分离；脚本只做增量；或脚手架目录与源码目录分开

### 26. 批量删除被拦截
- **后果**：打包脚本 `rmtree` 资源包目录被沙箱/用户拒绝
- **正确做法**：生成类脚本**不做批量删除**，用覆盖合并

### 27. 在 `python -c "…"` 的字符串里用反引号
- **后果**：bash 先做命令替换，写进记忆文件的内容被"掏空"（文件损坏）
- **正确做法**：长文本一律用 Write/Edit 工具写文件；脚本里不内嵌反引号字符串

### 28. 编译错误四连（都是低级但耗时）
- `<>` diamond（Java 1.6 不支持）、漏 `import java.util.ArrayList`、
  漏 getter（`currentAppId()`）、Lite 工程漏拷 stubs.jar 却留着依赖声明
- **正确做法**：新工程从模板复制时**逐项核对** dependencies/libs/imports；
  Java 1.6 规范打印在工程注释里

### 29. 没有先做像素预览就写工程
- **后果**：Demo v1/v2 的错误直到实机才暴露
- **正确做法**：**先在 PIL 里按 640×480 合成预览 → 与真值图算 MAE → 确认再写工程**
  （这条流程建立后，Demo3 一次过）

### 30. 错值写进文档后没有全局清理
- **后果**：警告图标 (74,4) 写进了 HANDOFF —— 错误会传染给接手的 AI
- **正确做法**：修正任何真值时，**全局搜索旧值**（代码+文档+脚本）同步更新；
  本项目里 (74,4) 就同时存在于 MainActivity、HANDOFF、preview 脚本三处

## 六、最该记住的五条（如果只读五条）

1. **先 dump 再写**：每个数字都要能报出处
2. **十六进制换算禁止心算**，用脚本复核；改"已验证的值"前必须重看 dump 原文
3. **能复用已验证的产物**（XML 布局、重建好的 9-patch），不要重写一遍引入新错
4. **一个屏有任何一个"大概"的数字，就不许编译**
5. **修真值必须全局同步**（代码/文档/脚本三处），错值会传染给下一手
